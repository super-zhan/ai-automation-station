# RAG检索质量评测实战：从Embedding选型到自动化评估流水线搭建

## 痛点：为什么你的RAG系统"看起来能跑，一用就废"？

构建RAG系统时，大家通常关注 Prompt 设计和 LLM 选型，却忽视了最关键的环节——**检索质量**。检索如果不准，LLM再强也白搭。我踩过几个月的坑后发现：embedding模型选型、chunk策略、检索参数调优这三件事不做量化评估，系统就是盲人摸象。

本文分享一套可落地的检索质量评测方案，包含自动化评估流水线的完整代码，以及在真实项目中的选型对比数据。

## 检索质量的核心指标

评测检索质量不能只靠感觉，需要量化指标：

| 指标 | 计算方式 | 含义 |
|------|---------|------|
| **Hit Rate@K** | 命中相关文档的比例 | 检索系统能不能找到对的资料 |
| **MRR (Mean Reciprocal Rank)** | 第一个相关结果的排名的倒数均值 | 第一个结果够不够准 |
| **NDCG@K** | 归一化折损累计增益 | 排序质量，是否把最相关的排前面 |
| **Precision/Recall@K** | 前K个结果中的精确率和召回率 | 结果集的纯度与覆盖度 |

生产环境中我主要盯 **Hit Rate@3** 和 **MRR**，前者保证"能找到"，后者保证"第一个就准"。

## 自动化评估流水线实现

### 1. 构建测试数据集

评估需要人工标注的测试集。每个样本包含：query、chunk_id、relevance_score(0/1)。

```python
# evaluation_dataset.py
from dataclasses import dataclass, field
from typing import List

@dataclass
class EvalSample:
    query: str
    relevant_chunk_ids: List[str]  # 可能多个相关片段
    metadata: dict = field(default_factory=dict)

@dataclass
class EvalDataset:
    samples: List[EvalSample]
    
    @classmethod
    def from_jsonl(cls, path: str) -> "EvalDataset":
        import json
        samples = []
        with open(path) as f:
            for line in f:
                data = json.loads(line)
                samples.append(EvalSample(
                    query=data["query"],
                    relevant_chunk_ids=data["relevant_chunk_ids"]
                ))
        return cls(samples=samples)
```

标注时有个经验：**每个query标注2-5个相关片段**，因为真实场景中答案可能分布在不同段落。只标注1个会导致召回率偏低、干扰模型对比判断。

### 2. 评估引擎核心

```python
# retrieval_evaluator.py
import numpy as np
from typing import List, Dict, Callable

class RetrievalEvaluator:
    def __init__(self, retriever_fn: Callable):
        """
        retriever_fn: query -> List[Dict], 每个dict有chunk_id, score
        """
        self.retriever = retriever_fn
    
    def evaluate(self, dataset: EvalDataset, k: int = 5) -> Dict:
        hit_rates = []
        mrrs = []
        precisions = []
        
        for sample in dataset.samples:
            results = self.retriever(sample.query, top_k=k)
            retrieved_ids = [r["chunk_id"] for r in results]
            relevant = set(sample.relevant_chunk_ids)
            
            # Hit Rate@K
            hits = sum(1 for rid in retrieved_ids if rid in relevant)
            hit_rates.append(1.0 if hits > 0 else 0.0)
            
            # MRR
            for rank, rid in enumerate(retrieved_ids, 1):
                if rid in relevant:
                    mrrs.append(1.0 / rank)
                    break
            else:
                mrrs.append(0.0)
            
            # Precision@K
            precisions.append(hits / k)
        
        return {
            "hit_rate_at_k": np.mean(hit_rates),
            "mrr": np.mean(mrrs),
            "precision_at_k": np.mean(precisions),
            "num_samples": len(dataset.samples)
        }
```

### 3. 集成多种检索策略做A/B对比

```python
# benchmark_runner.py
import chromadb
from sentence_transformers import SentenceTransformer

def build_retriever(
    collection_name: str,
    embedding_model: str = "BAAI/bge-large-zh-v1.5",
    search_type: str = "similarity",
    search_kwargs: dict = None
):
    """构建带统一接口的retriever，方便不同策略对比"""
    client = chromadb.PersistentClient(path="./chroma_db")
    model = SentenceTransformer(embedding_model)
    
    def retriever_fn(query: str, top_k: int = 5) -> list:
        query_emb = model.encode(query).tolist()
        collection = client.get_or_create_collection(
            name=collection_name,
            metadata={"hnsw:space": "cosine"}
        )
        results = collection.query(
            query_embeddings=[query_emb],
            n_results=top_k
        )
        return [
            {"chunk_id": id_, "score": dist}
            for id_, dist in zip(results["ids"][0], results["distances"][0])
        ]
    
    return retriever_fn

# 不同embedding模型对比
models_to_test = [
    "BAAI/bge-large-zh-v1.5",      # 国产首选，中文强
    "BAAI/bge-small-zh-v1.5",      # 轻量版
    "text-embedding-3-small",       # OpenAI
    "intfloat/e5-mistral-7b-instruct",  # 大模型级
]

# 不同chunk策略对比
chunk_strategies = [
    {"name": "fixed_256", "chunk_size": 256, "overlap": 20},
    {"name": "fixed_512", "chunk_size": 512, "overlap": 40},
    {"name": "fixed_1024", "chunk_size": 1024, "overlap": 80},
    {"name": "recursive_512", "chunk_size": 512, "overlap": 40, "separators": ["\n\n", "\n", "。", "！", "？", "；"]},
]
```

## 实测对比结果

在一份中文技术文档数据集（2300个chunk，200条标注query）上的对比：

### Embedding模型 Hit Rate@5

| 模型 | Hit Rate@5 | MRR | 推理延迟(ms) | 模型大小 |
|------|-----------|-----|-------------|---------|
| bge-small-zh-v1.5 | 0.782 | 0.521 | 8 | 33MB |
| bge-large-zh-v1.5 | **0.874** | **0.643** | 45 | 330MB |
| text-embedding-3-small | 0.835 | 0.598 | 120* | - |
| e5-mistral-7b | 0.891 | 0.661 | 1200 | 14GB |

*注：text-embedding-3-small依赖API调用，延迟包含网络

**结论**：bge-large-zh-v1.5 是性价比最优选择，bge-small适合对延迟极度敏感的场景。e5-mistral-7b虽然指标最好，但本地部署门槛太高。

### Chunk策略 Hit Rate@5（统一使用bge-large-zh）

| 策略 | Hit Rate@5 | 平均chunk长度 | 索引大小 |
|------|-----------|-------------|---------|
| fixed_256 | 0.821 | 256 | 45MB |
| fixed_512 | 0.853 | 512 | 22MB |
| fixed_1024 | 0.847 | 1024 | 11MB |
| recursive_512 | **0.881** | 487 | 24MB |

recursive_512在语义边界切分，保留了更完整的上下文，hit rate最高。fixed_256虽然粒度细但信息碎片化严重。

## 踩坑记录

### 坑1：余弦相似度 vs 点积

ChromaDB 默认 `hnsw:space` 是 `l2`（欧几里得距离），但 sentence-transformers 输出的 embedding 通常用余弦相似度更准。需要在创建collection时显式指定：

```python
collection = client.create_collection(
    name="my_docs",
    metadata={"hnsw:space": "cosine"}  # 默认是l2！
)
```

忘记这个配置会让检索质量暴降10-15%，我当时排查了一整天。

### 坑2：评估集泄露

标注评估集时用了和建索引相同的文档来源，但chunk边界不同，导致部分query的"相关片段"其实没在索引中。**解决方案**：评估集标注必须在chunk完成后，基于实际chunk_id来标注。

### 坑3：Hit Rate虚高

只用1个相关片段标注，bge-large 的 hit rate@3 能到 0.95 以上，看起来很美。但实际使用时用户问法更复杂，命中率掉到0.7。**解决**：每个query标注3-5个片段，模拟真实的多角度检索需求。

## 自动化评估流水线（CI集成版）

最终把评估集成到了CI中，每次索引更新自动跑：

```python
# ci_eval_pipeline.py
import json
import sys
from pathlib import Path

def run_eval_pipeline():
    # 1. 加载标注集
    dataset = EvalDataset.from_jsonl("data/eval_queries.jsonl")
    
    # 2. 构建retriever（使用当前索引）
    retriever = build_retriever(
        collection_name="production_v2",
        embedding_model="BAAI/bge-large-zh-v1.5"
    )
    
    # 3. 评估
    evaluator = RetrievalEvaluator(retriever)
    results = evaluator.evaluate(dataset, k=5)
    
    # 4. 写入结果
    output_path = Path("eval_results.json")
    with open(output_path, "w") as f:
        json.dump(results, f, indent=2)
    
    # 5. 阈值检查
    threshold = {"hit_rate_at_k": 0.80, "mrr": 0.55}
    passed = all(
        results[k] >= v for k, v in threshold.items()
    )
    
    if not passed:
        print(f"❌ 评估未通过: {results}")
        sys.exit(1)
    
    print(f"✅ 评估通过: {results}")

if __name__ == "__main__":
    run_eval_pipeline()
```

每次chunk策略变动、embedding模型升级、或新增文档后，CI流水线自动跑一遍评估，低于阈值直接阻断发布。配合GitHub Actions效果很好。

## 进阶方向

1. **混合检索**：结合BM25关键词检索和语义检索，用RRF（Reciprocal Rank Fusion）合并结果，一般能再提升3-5%的Hit Rate
2. **基于LLM的评估**：用GPT-4等模型对检索结果做更细粒度的相关性判断，替代人工标注
3. **在线评估**：在生产环境埋点，记录用户点击/反馈，形成eval兜底数据，与离线评估互为补充
4. **query改写优化**：对用户query做改写/扩展后再检索，尤其适合短query场景

RAG系统的天花板不在模型，在检索。把检索质量量化评估这步做好，你的RAG才算真正"能打"。
