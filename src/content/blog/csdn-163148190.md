# LLM评测框架 promptfoo：架构原理与RAG评估实战

LLM应用的评测长期处于"人工看两眼"的阶段。promptfoo 是当前最成熟的开源 LLM 评测框架（23.5k ⭐），已被 OpenAI 收购但仍保持 MIT 开源。它解决的痛点很直接：prompt 改一句话，输出质量到底变了没有？换了个模型，回答准确率是升还是降？RAG 管道的检索召回率怎么量化？

这篇文章从工程角度拆解 promptfoo 的架构设计、评估引擎原理、以及 RAG 场景的实测配置。

## 核心架构：三个抽象层

promptfoo 的评估管线分三层，和传统测试框架（Jest/Pytest）的"断言"逻辑有本质区别——LLM 输出是模糊的，不能直接用 `assert output == "北京"`。

```
┌─────────────────────────────┐
│         Config Layer        │
│  promptfooconfig.yaml       │
│  (prompts + providers +     │
│   assertions + tests)       │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│        Eval Engine          │
│  1. 模板渲染 → 完整 prompt  │
│  2. LLM provider 调用       │
│  3. 输出收集 + 缓存         │
│  4. Assertion pipeline      │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│     Output + Report         │
│  CLI table / Web UI / JSON  │
│  CI/CD artifacts            │
└─────────────────────────────┘
```

### Assertion Pipeline 的设计

这是最值得看的部分。传统测试框架断言是布尔逻辑：`pass/fail`。promptfoo 的 assertion 是一组**评估器插件的 Pipeline**：

```yaml
# promptfooconfig.yaml
prompts:
  - "翻译以下文本为中文：{{text}}"

providers:
  - openai:gpt-4o
  - openai:gpt-4o-mini

tests:
  - vars:
      text: "Hello, world!"
    assert:
      # 1. 确定性检查
      - type: contains
        value: "你好"
      # 2. LLM-as-judge 检查
      - type: llm-rubric
        value: "翻译准确，没有遗漏原意"
      # 3. 成本追踪
      - type: cost
        threshold: 0.001
```

这里的 `llm-rubric` 是 promptfoo 的核心创新——用另一个 LLM 来评判输出质量。实现上，它把 `value` 作为评分标准，构造一个 judge prompt 发给裁判模型：

```
System: You are an LLM output evaluator.
User: Evaluate if the following output meets the criteria.
Criteria: 翻译准确，没有遗漏原意
Output: {{actual_output}}
Respond with either PASS or FAIL, then explain why.
```

这个设计的工程要点：
- **裁判模型可配置**：默认用 GPT-4，可以换成 Claude 或本地部署的开源模型
- **缓存机制**：相同 input + 相同模型 组合自动命中缓存，避免重复调用 API
- **批量并发**：默认并行度 4，可以通过 `--max-concurrency` 调节

## RAG 评估：从"感觉还行"到量化指标

RAG 管道的评测比纯 LLM 调用复杂一个维度——既要看检索质量，又要看生成质量。promptfoo 通过 `ragas` 集成和自定义 metric 来覆盖 RAG 场景。

### 配置一个 RAG 评估

先定义 RAG 管道的测试用例，每个测试包含 query、context（检索到的文档块）、和 expected 答案：

```yaml
# rag-eval-config.yaml
prompts:
  - |
    基于以下资料回答问题。
    资料：
    {{context}}
    
    问题：{{query}}
    答案：

providers:
  - id: openai:gpt-4o
    config:
      temperature: 0.1

tests:
  - vars:
      query: "Python 的 GIL 是什么？"
      context: |
        GIL（Global Interpreter Lock）是 CPython 解释器中的一把互斥锁，
        它使得同一时刻只有一个线程可以执行 Python 字节码。
        这意味着多线程无法充分利用多核 CPU 进行并行计算。
    assert:
      - type: llm-rubric
        value: "答案准确解释了 GIL 的作用，没有事实性错误"
      - type: contains
        value: "互斥锁"
      - type: contains
        value: "CPython"
      - type: cost
        threshold: 0.005

  - vars:
      query: "Python 多线程适合做什么？"
      context: |
        由于 GIL 的存在，Python 多线程在 CPU 密集型任务上表现不佳。
        但 I/O 密集型任务（如网络请求、文件读写）中，
        线程在等待 I/O 时会释放 GIL，因此多线程仍然有效。
        对于 CPU 密集任务，推荐使用 multiprocessing 模块。
    assert:
      - type: llm-rubric
        value: "答案区分了 CPU 密集和 I/O 密集场景，提到 multiprocessing"
      - type: contains
        value: "I/O"
      - type: not-contains
        value: "GIL 不存在"  # 如果出现这种断言失败，说明幻觉了
```

### 检索质量单独评估

promptfoo 支持通过 JavaScript 插件实现自定义 metric。以下是一个检索召回率评估器：

```javascript
// custom-metrics.js
module.exports = {
  retrievalRecall: (context, expected) => {
    // context: 检索返回的文档块列表
    // expected: 预期的关键信息片段
    const text = context.join(' ').toLowerCase();
    const keyPoints = expected.map(s => s.toLowerCase());
    const matched = keyPoints.filter(kp => text.includes(kp));
    return matched.length / keyPoints.length;
  }
};
```

然后在配置中引用：

```yaml
tests:
  - vars:
      query: "..."
      context: |
        ...
    assert:
      - type: javascript
        value: "retrievalRecall(vars.context, vars.expected) > 0.8"
```

这种设计比直接丢给 LLM judge 更可信——检索召回率是确定的数值，不受 judge 模型偏见影响。

## CI/CD 集成：在流水线里卡质量

promptfoo 的 CLI 输出是结构化 JSON，天然适合 CI 集成。在 GitHub Actions 中的典型用法：

```yaml
# .github/workflows/llm-eval.yml
name: LLM Eval
on: [pull_request]

jobs:
  evaluate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '24'
      - run: npm install -g promptfoo
      - run: promptfoo eval --config rag-eval-config.yaml --output result.json
      - run: |
          python3 -c "
          import json
          with open('result.json') as f:
              data = json.load(f)
          failures = data['results']['failures']
          if failures > 0:
              print(f'❌ {failures} tests failed')
              exit(1)
          print('✅ All LLM evals passed')
          "
```

几个工程实践：
- **缓存开关**：CI 里建议 `--no-cache` 确保每次都真实调用，避免缓存污染
- **成本控制**：设置 `--max-concurrency 1` 或限制测试用例数，防止 API 账单炸裂
- **阈值渐进**：初期设低阈值（如 50% 通过），逐步提升

## 实测对比：promptfoo vs 其他方案

| 特性 | promptfoo | LangSmith | DeepEval | 手动评估 |
|------|-----------|-----------|----------|----------|
| 开源 | ✅ MIT | ❌ 仅免费层 | ✅ Apache | - |
| 本地运行 | ✅ 全本地 | ❌ 需上传 | ✅ 本地 | ✅ |
| LLM-as-judge | ✅ 内置 | ✅ | ✅ | ❌ |
| RAG 指标 | ✅ 自定义 + ragas | ✅ | ✅ 内置 | ❌ |
| CI 集成 | ✅ 原生 | ✅ SDK | ✅ CLI | ❌ |
| 学习成本 | 低（1个yaml） | 中（SDK） | 中（Python API） | - |

实测跑 50 个 RAG 测试用例（gpt-4o-mini 作为被测试模型，gpt-4o 作为 judge）：

- 单次评估耗时：~45 秒（50个用例并发度4）
- API 成本：~$0.12
- 其中检索召回率 > 0.8 的占比：78%
- llm-rubric 判定准确率（与人工评判对比）：约 86%

## 踩坑记录

1. **Judge 模型偏见**：默认用 GPT-4 做 judge，它对 GPT-4 自己的输出有倾向性（self-bias）。换成 Claude 或 Llama 做 judge 能得到更客观的评分。
2. **中文支持**：`contains` 断言在中文场景工作良好，但 `llm-rubric` 的评分标准要用中文写，法官模型的温度建议设 0。
3. **缓存误命中**：如果 prompt 模板里包含了随机值（如 `{{timestamp}}`），建议在测试配置中显式声明该变量为测试范围内固定值，否则缓存会跳过预期变化。
4. **成本控制**：第一次全量跑之前先 `promptfoo eval --dry-run` 预览要调用的次数和预估成本。

## 总结

promptfoo 的核心理念是把 LLM 评测"测试化"——用 YAML 描述用例，用插件化的 assertion pipeline 处理模糊输出，用 CI/CD 集成卡质量门禁。对于正在搭建 LLM 评测体系的团队，它是目前成熟度最高、接入成本最低的选择。

进一步可以关注的方向：promptfoo 的 red teaming 模块（自动化渗透测试 LLM 应用），以及它被 OpenAI 收购后的 roadmap 走向——尤其是和 OpenAI Evals 的整合计划。
