# LLM 评估实战：用 Evidently 构建 AI 测试流水线

大模型上线不只是调 API。Prompt 改一个字、Embedding 模型升个版本、RAG 文档库加一批新数据——每项变更都可能让输出质量断崖下跌。没有测试体系的 AI 应用，本质上是在生产环境里盲飞。

Evidently 是当前社区最活跃的开源 LLM 评估框架（7.7k⭐），提供 100+ 指标覆盖从文本质量到数据漂移的全链路检测。这篇文章不讲概念，直接拆解如何用 Evidently 搭建一套可落地的 LLM 测试流水线：指标选型、测试用例设计、CI 集成、以及我们踩过的坑。

## 核心架构：Preset + Metric + Test

Evidently 的评估体系分三层：

```
数据输入 → Preset（预设套件） / Metric（单指标） → Test（断言条件）
           ↘ Test Suite（组合） → Report / Test Result
```

- **Preset**：预配置的评估组合，开箱即用（`TextEvalPreset`、`RAGPreset`）
- **Metric**：原子指标，可自由组合（`F1Score`、`ExactMatch`、`Faithfulness`）
- **Test**：给指标加上阈值，变成可断言的测试用例
- **Test Suite**：把多个 Test 打包，一次性跑完整评估

这种分层设计的核心好处是：开发阶段用 Preset 快速验证，CI 里用 Test Suite 做回归断言，线上用 Metric 做实时监控——三套配置复用同一套指标定义。

## 实战：搭建 LLM 问答系统的评估流水线

### 1. 安装与基础配置

```python
pip install evidently evidently[llm]
```

初始化评估器时需要指定 LLM 客户端（用于评估回答质量，如 faithfulness 等需要 LLM-as-Judge 的指标）：

```python
from evidently import ColumnMapping
from evidently.metrics import (
    ExactMatchScore,
    F1Score,
    FaithfulnessScore,
    ContextRecall,
    ContextPrecision,
)
from evidently.options import OptionProvider
from evidently.options.llm import LLMOptions

import openai

llm_client = openai.OpenAI(
    api_key="sk-...",
    base_url="https://api.openai.com/v1",
)

options = OptionProvider()
options.add(LLMOptions(llm_client=llm_client, eval_model="gpt-4o"))

column_mapping = ColumnMapping(
    question="question",
    answer="answer",
    expected_answer="expected_answer",
    context="context",
)
```

### 2. 定义测试数据集

Evidently 的评估输入是一个 Pandas DataFrame，每行是一个 QA 样本：

```python
import pandas as pd

eval_data = pd.DataFrame([
    {
        "question": "什么是 RAG？",
        "answer": "RAG（Retrieval-Augmented Generation）是一种将检索与生成结合的架构，先在知识库中检索相关文档片段，再基于检索结果生成回答。",
        "expected_answer": "RAG 是检索增强生成，结合检索和生成两步完成问答。",
        "context": "Retrieval-Augmented Generation (RAG) is a technique that combines retrieval from a knowledge base with text generation.",
    },
    {
        "question": "Python 的 GIL 是什么？",
        "answer": "GIL（Global Interpreter Lock）是 CPython 的全局解释器锁，确保同一时刻只有一个线程执行 Python 字节码。",
        "expected_answer": "GIL 是 CPython 的全局解释器锁。",
        "context": "The Python Global Interpreter Lock (GIL) is a mutex that protects access to Python objects.",
    },
])
```

### 3. 执行评估：单个 Test Suite

```python
from evidently.test_preset import TextEvalTestPreset
from evidently.tests import TestF1Score, TestExactMatchScore, TestFaithfulnessScore
from evidently.test_suite import TestSuite

suite = TestSuite(
    tests=[
        TextEvalTestPreset(),
        TestF1Score(gte=0.7),
        TestFaithfulnessScore(gte=0.9),
    ],
    options=options,
    column_mapping=column_mapping,
)

suite.run(current_data=eval_data)
suite.save_html("llm_eval_report.html")
```

`TextEvalTestPreset` 会自动添加以下指标的默认断言：
- Exact Match (EM) ≥ 0.5
- F1 Score ≥ 0.7
- Precision ≥ 0.7
- Recall ≥ 0.7
- Faithfulness ≥ 0.9

这份 HTML 报告里包含了每个测试用例的详细结果、失败原因、以及分布图表，可以直接作为 CI 产物存档。

### 4. 程序化判断：用于 CI/CD

```python
result = suite.as_dict()

if result["summary"]["failed_tests"] > 0:
    print(f"❌ 评估未通过！{result['summary']['failed_tests']} 个测试失败")
    for test in result["tests"]:
        if test["status"] == "FAILED":
            print(f"  - {test['name']}: {test['description']}")
    exit(1)
else:
    print("✅ 全部测试通过")
```

## RAG 评估：不只是 QA 匹配

对于 RAG 系统，单纯看 F1/EM 远远不够。检索质量直接影响生成质量。Evidently 提供了专门的 RAG 指标：

```python
from evidently.metrics import (
    ContextRecall,
    ContextPrecision,
    ContextEntityRecall,
)

rag_metrics = [
    ContextRecall(),
    ContextPrecision(),
    ContextEntityRecall(),
]
```

| 指标 | 含义 | 评估方式 |
|------|------|---------|
| Context Recall | 检索到的上下文是否覆盖了回答所需信息 | LLM 判断 |
| Context Precision | 检索到的上下文中有多少是回答实际用到的 | LLM 判断 |
| Context Entity Recall | 回答中的实体是否在上下文中存在 | 规则匹配 |

有个常见的误区：Context Precision 高不一定好。如果你只用 top-1 chunk 且恰好命中，Precision 是 100%，但 Recall 可能只有 20%。

我们在生产中的经验是：**Context Recall 和 Faithfulness 要联合监控**。Recall 低说明检索漏了东西，Faithfulness 低说明 LLM 在编造。两者都低 → 检索问题；Recall 高但 Faithfulness 低 → LLM 指令跟踪问题。

## 漂移检测：生产环境持续监控

测试集通过只是开始。线上的数据分布会漂移——用户提问方式变了、文档库更新了、LLM 模型升级了。Evidently 的数据漂移检测模块可以量化这些变化：

```python
from evidently.metrics import (
    EmbeddingDistanceMetric,
    LLMEmbeddingDriftMetric,
)
from evidently.metrics.text_embedding_drift import TextEmbeddingDriftMetric

drift_metric = TextEmbeddingDriftMetric(
    stattest="wasserstein",
    stattest_threshold=0.05,
)

# 用 baseline（测试集）vs current（生产采样）做对比
drift_report = Report(metrics=[drift_metric])
drift_report.run(
    reference_data=eval_baseline,
    current_data=production_sample,
    column_mapping=column_mapping,
)
```

我们在生产环境中部署了一个 30 分钟的定时任务，采样过去半小时的线上请求，与测试基线做漂移对比。一旦漂移分超过阈值，自动触发重新评估流程：

- 漂移 > 0.1：发告警通知
- 漂移 > 0.2：自动拉取最新数据追加到测试集
- 漂移 > 0.3：阻断自动发布流水线

## 踩坑记录

### 1. LLM-as-Judge 的成本和延迟

Faithfulness、Context Recall 等指标依赖 LLM 做裁判。1000 条测试数据跑一次评估 ≈ 2000-3000 次 LLM 调用（每条样本可能需要多次 LLM 交互）。我们的方案：

- 测试集保留 100-200 条充分标注的核心样本
- 使用 `gpt-4o-mini` 做评估，`gpt-4o` 做抽样交叉验证
- 缓存 LLM 评判结果（相同输入不重复调用）

### 2. 中文场景的 Embedding 漂移检测

Evidently 默认的 `text_embedding_drift` 使用 `text-embedding-ada-002`。我们的中文业务场景下，改用 `text-embedding-3-small` 后漂移分普遍偏高——不是数据真变了，是 Embedding 空间分布变了。最终用 `bge-m3` 本地部署来解决，同时将 wasserstein 阈值从 0.05 放宽到 0.08。

### 3. Test Suite 的权重陷阱

把所有测试设成 `gte=0.9` 是不现实的。Faithfulness 可以设高阈值（0.9+），但 F1/EM 取决于任务难度。开放生成类问题（如"总结一下"）的 F1 天然低于固定答案类问题（如"巴黎在哪"）。

我们按问题类型分组设置不同阈值：

```python
test_suites = {
    "extractive": {"f1": 0.8, "em": 0.7, "faithfulness": 0.95},
    "abstractive": {"f1": 0.5, "faithfulness": 0.9},
    "classification": {"em": 0.85, "f1": 0.85},
}
```

## 总结

Evidently 的价值不在于指标有多花哨，而在于它把 LLM 评估这件事从"人工看几条结果拍脑袋"变成了"可复现、可断言、可 CI 集成"的工程实践。

**下一步可以做的方向：**
1. 用 Evidently 的 `Report` API 搭建线上监控 Dashboard
2. 集成到 CI 流水线，每次 Prompt/Model 变更自动触发回归测试
3. 结合人工标注反馈，用评估结果反哺测试集迭代
4. 对比不同 LLM 在同样测试集上的表现，做模型选型决策

LLM 应用的工程质量，取决于你愿意在测试上投入多少。Evidently 给了你武器，剩下的就是构建测试文化。
