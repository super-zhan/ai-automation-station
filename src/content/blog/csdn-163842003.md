# Agentic 测试脚手架：Constitution + PreToolUse Hook，让 AI 写不出"违宪"的测试代码

让 AI 写 E2E 测试，最大的坑不是它不会写，而是它每次写的风格都不一样：这次给你 XPath，下次给你 `waitForTimeout(5000)`，再下次掏出 `any` 和魔法数字。prompt 里写一百遍"不要用硬等待"也没用——规则在 prompt 层只是"建议"，AI 会忘、会妥协、会在上下文变长之后悄悄违反。GitHub 上 2026-08 新出的 agentic-playwright（idavidov13/agentic-playwright，MIT，98★）给的解法是把规则拆成两层：**prompt 层的 Constitution（MUST/SHOULD/WON'T 三档规则 + 17 个 skill）** 和 **机械层的 PreToolUse Hook（`enforce_constitution.py`，在文件落盘之前就把违禁模式拦下来）**。规则是建议，拦截是保证——这比任何"AI 提示词工程"都可靠，因为后者依赖模型自觉，前者是确定性代码。

## 一、Constitution：把规则分成 MUST / SHOULD / WON'T 三档

项目根目录的 `CLAUDE.md`（以及 Cursor 的 `rules.mdc`、Copilot 的 `copilot-instructions.md`）就是"宪法"全文，所有 AI 工具启动时自动加载。三档规则的分工很清晰：

| 档位 | 定位 | 典型条目 |
| --- | --- | --- |
| MUST | 架构级强制 | 测试只能从 `fixtures/pom/test-options.ts` 导入 `test`/`expect`；页面对象必须走 fixture 依赖注入，禁止 `new LoginPage(page)`；API schema 一律 `z.strictObject()`；响应校验必须 `expect(Schema.parse(body)).toBeTruthy()` |
| SHOULD | 推荐实践 | 用 Faker factory 生成 happy-path 数据；用 `test.step()` 组织 Given/When/Then；JSDoc 只加在 action 方法上 |
| WON'T | 机械可检测的禁忌 | 无 XPath、无 `waitForTimeout`、无 `any`、无 `z.object()`、无 JSON 静态数据、无 `@functional` 标签、标签不许挂在 `test.describe()` 上 |

注意 WON'T 这一档的选材逻辑：**每一条都是字符串或 AST 层面可检测的模式**。`waitForTimeout(`、`z.object(`、XPath 特征符、`@playwright/test` 的 import 路径——这些不需要理解语义，正则就能扫出来。这就是为什么它们能升级成"机械拦截"，而 MUST 里那些需要判断语义的规则（比如"数据工厂该放哪"）只能停留在 prompt 层。规则分档的本质，是把"模型能力问题"降维成"字符串匹配问题"。

同一个 prompt（"给商品搜索写个测试"）喂给同一个 AI，有规则和没规则的结果对比：

```ts
// ❌ 无规则：XPath、硬等待、any、魔法数字、无结构
test('search', async ({ page }) => {
    await page.goto('https://practicesoftwaretesting.com');
    await page.locator('//input[@id="search-query"]').fill('pliers');
    await page.locator('//button[@type="submit"]').click();
    await page.waitForTimeout(5000);
    const cards: any = await page.$$('.card');
    expect(cards.length > 0).toBe(true);
});

// ✅ 有规则：fixture 导入、Given/When/Then 步骤、web-first 断言
import { expect, test } from '../../../fixtures/pom/test-options';

test('should show only matching products when searching',
    { tag: '@regression' },
    async ({ homePage }) => {
        await test.step('GIVEN the user is on the home page', async () => {
            await homePage.open();
        });
        await test.step('WHEN the user searches for "pliers"', async () => {
            await homePage.searchFor('pliers');
        });
        await test.step('THEN every result matches the search term', async () => {
            await expect(homePage.searchCaption).toContainText('pliers');
            await expect(homePage.productNames.first()).toContainText('Pliers');
        });
    });
```

## 二、PreToolUse Hook：把 WON'T 变成物理闸门

规则写得再好，AI 还是会违反。所以项目在 `.claude/settings.json` 里注册了一个 `PreToolUse` hook（matcher 为 `Write|Edit|MultiEdit`），用 Python 脚本 `enforce_constitution.py` 做机械兜底。机制是 Claude Code 的 hook 协议：**hook 进程从 stdin 读入 pending tool call 的 JSON（含 tool_name 和 tool_input），返回 exit code 2 就阻断这次写入，并把 stderr 消息回传给 agent**。

```
AI 生成 Write/Edit/MultiEdit
        │
        ▼
Claude Code 把 tool call payload 通过 stdin 交给 hook
        │
        ▼
enforce_constitution.py 检查目标文件 + 内容模式
        │
        ├── 命中 WON'T 模式 ──► exit 2，消息回传 agent，写入被拒
        └── 未命中 ──► exit 0，放行
```

它拦截的七类机械可检测违规：

| 被拦截的模式 | 对应规则 |
| --- | --- |
| spec/setup 文件里 `@playwright/test` 的 import | 必须从 `fixtures/pom/test-options.ts` 导入 |
| 任何 `.ts` 里的 `waitForTimeout(` | 禁止硬等待 |
| schema 文件里的 `z.object(` | 必须 `z.strictObject()` |
| `pages/**`、`tests/**` 里的 XPath | 禁止 XPath |
| `test-data/static/` 下的 `.json` | 静态数据必须是 `.ts` + `as const` |
| spec 里的 `@functional` 标签 | 单标签规则，只允许六个规范标签 |
| `test.describe()` 内的标签 | 标签只能打在单个 test 上 |

这个 hook 有一个很容易被忽略但很关键的设计决策：**malformed payload 和非目标文件一律放行**——hook 永远不因为自身基础设施出错而阻断开发。拦截逻辑可以漏，但不能误伤；宁可让一条违规溜过去，也不能让 hook 的 bug 卡死整个开发流程。这是所有"门禁类工具"都该抄的安全边界。

## 三、fixture 分层组合：单一导入点 + mergeTests

测试代码的组织上，脚手架的核心是"单一导入点"：所有 spec 只能从 `fixtures/pom/test-options.ts` 导入 `test` 和 `expect`，页面对象、API 请求、setup/teardown 全部通过 fixture 依赖注入，禁止在测试里手动 `new`：

```
                        test-options.ts（测试唯一导入点）
                                    │
            ┌───────────────────────┼───────────────────────┐
      mergeTests()            mergeTests()            mergeTests()
            │                       │                       │
┌───────────▼───────────┐  ┌────────▼───────────┐  ┌────────▼────────────┐
│ page-object-fixture   │  │ api-request-fixture│  │ helper-fixture      │
│ • appPage: AppPage    │  │ • apiRequest<T>()  │  │ • createdResource   │
│ • resetStorageState() │  │   （泛型 + Zod 校验）│  │ • 业务 setup/teardown│
└───────────┬───────────┘  └────────┬───────────┘  └────────┬────────────┘
            │                       │                       │
       pages/AppPage        fixtures/api/schemas/    fixtures/api/
       （getter locator）     （Zod schema）          plain-function.ts
```

三层各自独立，`mergeTests()` 组合而不耦合。这个架构的收益不止是"分层清晰"：**单一导入点让 hook 的 import 检查变得可行**——如果允许散装导入，`@playwright/test` 的拦截规则根本无从写起。架构约束和机械拦截在这里是互相成就的：先定死唯一入口，才谈得上在入口处设卡。页面对象内部要求 locator 用 getter 而不是属性初始化，且按"交互元素 / 反馈校验元素 / action 方法"三段式组织，配合 `getByRole`、`getByLabel` 这类语义定位器，AI 生成时选择空间被压缩到最小。

## 四、API 契约测试：strictObject 拒绝静默剥离

API 侧用 `apiRequest` fixture 包了一层，配合 Zod schema 做运行时校验。两个值得抄的细节：

1. **`z.strictObject()` 而不是 `z.object()`**。`z.object()` 默认剥离未知字段，后端多返回一个字段你的测试照样绿——契约漂移被静默吞掉。`strictObject` 直接抛错，多一个字段就是红。契约测试的意义就在于"多退少补都要报"，宽松 schema 等于没测。
2. **响应断言必须是 `expect(SchemaName.parse(body)).toBeTruthy()` 这个精确形态**。项目明确禁止"类型泛型或裸 `Schema.parse(body)`"——前者只校验类型不校验运行时，后者不产生断言。另外对 400 错误测试有硬性要求：禁止只测"空 body 的 400"，每个字段都要做逐字段缺失 + 非法类型的 `for...of` 循环测试。

```ts
// fixture/api/schemas/app/userSchema.ts
import { z } from 'zod';

export const UserResponseSchema = z.strictObject({
    id: z.string().uuid(),
    email: z.string().email(),
    roles: z.array(z.enum(['ADMIN', 'USER'])),
});

// tests/app/api/login.spec.ts
test('POST /login returns the user contract', { tag: '@api' }, async ({ apiRequest }) => {
    const body = await apiRequest<UserResponseSchema>({
        method: 'POST',
        url: '/login',
        data: { email: 'a@b.com', password: 'x' },
    });
    expect(UserResponseSchema.parse(body)).toBeTruthy();
});
```

配套还有"No Silent Coverage Drops"原则：OpenAPI 文档里出现的每个状态码都必须有测试——要么通过、要么失败、要么 `test.skip` + `// FIXME:` 注明原因，不允许悄悄不测。这直接堵住了"AI 遇到后端 bug 就自动绕开"的偷懒路径。

## 五、三棵规则树：多工具的镜像同步是个真问题

规则不只服务 Claude Code，还要在 Cursor 和 GitHub Copilot 里生效，于是有了三份镜像：`.claude/skills/`（按需读取）、`.cursor/skills/`（同上）、`.github/instructions/`（按 `applyTo` glob 自动注入）。README 自己承认：**三棵树之间的镜像 parity 是"手维护的纪律"**，不是自动保证的。项目为此上了三道闸：

- `check:skills-drift`：Constitution 规则必须锚定在所属 skill 的 Critical block 里，防止规则漂移；
- `check:skills-references`：遍历三棵树，抓断链指针、孤儿引用、失效锚点；
- `skills-lock.json`：记录 vendored 的 `skill-creator`、`playwright-cli` 上游文件的 SHA-256，`npm run skills:verify` 校验哈希一致性，防止本地改着改着跟上游脱节。

版本管理也用了同一套路：根目录 `VERSION` 文件是唯一事实源，`npm run check:version` 断言 `VERSION == package.json == CHANGELOG 最新标题`，不一致就 fail，挂在 pre-commit 和 CI 的 `skill-lint.yml` 里。**凡是"多处必须一致"的东西，都要用代码去校验，不要指望人记得**——这是这个项目贯穿始终的方法论。

## 六、实践与踩坑

上手很简单：`npm create agentic-playwright . -- --demo`，零问答，脚手架 + 依赖 + 浏览器装完直接跑 demo 应用的 smoke test，5 分钟内看到绿。标签系统值得单独说：每个测试**只能有一个标签**（`@smoke` / `@sanity` / `@regression` / `@e2e` / `@api` / `@destructive`），`@destructive` 最重、只用于动共享全局状态的测试、且不与任何其他标签组合。单标签规则让 CI 的过滤矩阵（`--grep @smoke` 之类）永远没有歧义。

实际用下来的坑：

1. **CRLF 换行问题**。Windows 上 `core.autocrlf=true` 会把脚本 checkout 成 CRLF，bind mount 进 Linux 容器后 shebang 变成 `#!/bin/bash\r`，报 `bash\r: No such file or directory`。`.gitattributes` 对新建 clone 有效，存量工作树要 `rm scripts/*.sh && git checkout -- scripts/` 重新归一化，用 `git ls-files --eol` 验证。
2. **playwright-cli 的浏览器缓存是独立的一份**。CLI 通过 wrapper 脚本隔离 `PLAYWRIGHT_BROWSERS_PATH`，跟 Playwright Test 的浏览器互不共享。`npx playwright install` 只解决测试浏览器，CLI 的要用 `npm run playwright-cli:install-browsers` 单独装。两个都缺就两个都报"Executable doesn't exist"。
3. **auth.setup.ts 失败 = 所有测试项目全跳过**。setup project 是所有 test project 的前置，登录态拿不到，后面全被 skip。排查时先确认 `APP_URL`/`API_URL` 可达、凭据有效、`createStorageState.ts` 里的登录表单选择器跟真实页面一致。
4. **本地绿、CI 红**。老三样：CI 里环境变量没配全（对照 `env/.env.example` 逐个核对）、CI 机器慢导致 timeout（在 `playwright.config.ts` 里调）、headless 差异（本地先跑 `npm run test:ci` 复现）。

工作流上项目反复强调一条黄金律：**Verify → Commit → Proceed**。每个 prompt 只做一件事，生成后先 review 再跑测试，绿了立刻 commit 形成 checkpoint，然后再开下一个 prompt。配合 `ai-native-workflow` skill 的置信度门禁（plan 必须带 `Confidence: 1-10` + `Rationale` + `Unknowns`，低于 5 必须停下来问人而不是硬编），把"AI 连续多步跑飞"的风险切成了一段段可回滚的原子操作。

## 七、配置细节：本地与 CI 的差异是设计出来的

`playwright.config.ts` 里本地和 CI 的差异不是随手调的，而是成体系的：

| 配置项 | 本地 | CI |
| --- | --- | --- |
| Workers | auto | 1 |
| Retries | 0 | 2 |
| Reporter | HTML（失败自动打开） | Blob + HTML |
| Trace | first retry | first retry |
| Screenshot / Video | 失败保留 | 失败保留 |

本地追求反馈速度（全并行、零重试），CI 追求稳定性（单 worker 避免资源竞争、重试 2 次吃掉偶发 flake、blob report 便于跨机器聚合）。超时体系也分层：test 60s、action 10s、navigation 30s、expect 10s——expect 超时最短，逼着你用 web-first 断言而不是等固定时间。多浏览器项目 `chromium` / `firefox` / `webkit` 默认只开 Chrome（另外两个注释掉），且全部 `dependencies: ['setup']`，用 Playwright 的 project dependency 机制保证登录态先于测试生成。`@destructive` 标签的测试默认被 `npm test` 排除，要跑必须显式 `npm run test:destructive`（单 worker 隔离执行）——共享状态测试和普通测试从命令层面就分开了。环境切换靠 `ENVIRONMENT=staging npm test` 读 `env/.env.<env>` 文件，生产环境只允许跑只读测试。

## 总结

这个项目最值得迁移的不是脚手架本身，而是三个思路：**规则分档**（能机械检测的进 WON'T，需要语义判断的留在 MUST/SHOULD，别混在一起）；**机械兜底**（prompt 规则永远只是建议，写时拦截才是保证，且拦截器必须"宁可漏、不可误伤"）；**验证再提交**（每次变更都跑测试并 commit，把 AI 的不可控性关进一个个可回滚的 checkpoint）。进阶方向：把字符串匹配升级成 AST lint 规则（能抓 `await page.locator(...).waitFor()` 这种变体，正则抓不到）、给规则本身写评估 CI（验证规则改动了之后 AI 输出质量确实变化）、以及用代码生成三棵规则树代替手工镜像同步。98★ 的项目，架构思路比很多千星项目值钱。
