# RAG检索质量测试：从Recall@k到LLM-as-judge的完整评估体系

RAG 系统上线后"答非所问"，90% 的根因不在生成模型，而在检索层：top-k 里根本没有正确答案。检索质量测不出来，后面所有优化（prompt、chunk、重排）都是盲调。这篇文章给出一套可落地的评估体系：离线阶段用 golden set 算 Hit Rate / Recall@k / MRR 这类确定性指标，在线阶段用 LLM-as-judge 算 faithfulness / context precision 这类语义指标，最后把阈值接进 CI 当质量门禁。两层指标缺一不可——离线指标告诉你"检没检到"，在线指标告诉你"答没答对"。

## 一、离线检索评估：先回答"检没检到"

离线评估的核心是构造 golden set：一批 `(question, golden_chunk_ids)` 标注对，问题来自线上真实 query 日志（脱敏后），golden chunk 由人工或半自动标注。规模不用大，100~300 条足够暴露检索层的系统性问题，重点是覆盖高频 query 类型和边界 case（同义改写、多跳问题、专有名词）。

评估代码不复杂，核心是算三个指标：

```python
def evaluate_retrieval(retriever, golden_set, k=5):
    """golden_set: list of {question, golden_ids:set}"""
    hit, mrr_sum, recall_sum = 0, 0.0, 0.0
    for item in golden_set:
        docs = retriever.search(item["question"], top_k=k)  # [(id, score)]
        retrieved = [d[0] for d in docs]
        hits = set(retrieved) & item["golden_ids"]
        # Hit Rate@k: top-k 里是否出现 golden chunk
        if hits:
            hit += 1
        # MRR: 第一个命中结果的倒数排名
        for rank, rid in enumerate(retrieved, start=1):
            if rid in item["golden_ids"]:
                mrr_sum += 1.0 / rank
                break
        # Recall@k: 命中的 golden chunk 占比
        recall_sum += len(hits) / len(item["golden_ids"])
    n = len(golden_set)
    return {"hit_rate@k": hit / n, "mrr@k": mrr_sum / n, "recall@k": recall_sum / n}
```

指标解读有一条容易踩的线：**Hit Rate 是"有没有救"，MRR 是"排得够不够靠前"**。Hit Rate 高但 MRR 低，说明答案在 top-k 里但被无关内容挤到了后面——这是重排（rerank）该上场的时候；Hit Rate 本身就低，问题在 embedding 或 chunk 切分，rerank 救不了。要求更高的场景可以上 NDCG@k，它对"相关程度分级"更敏感，但标注成本高，一般团队从 Hit Rate + MRR 起步就够。

我这边一个内部知识库项目的实测对比（300 条 golden set，Qdrant，bge-m3 embedding，k=5）：

| 检索方案 | Hit Rate@5 | MRR@5 | 说明 |
|---|---|---|---|
| 纯向量（bge-m3） | 0.71 | 0.42 | 专有名词/代码片段召回差 |
| 纯 BM25 | 0.66 | 0.38 | 同义表达召回差 |
| 混合检索 + RRF(k=60) | 0.84 | 0.55 | 两路互补，提升最明显 |
| 混合 + cross-encoder rerank | 0.87 | 0.71 | MRR 大幅改善，延迟 +80ms |

混合检索（dense + sparse）用 RRF 融合是性价比最高的第一步，代码就几行：

```python
from rank_bm25 import BM25Okapi
from numpy import argsort

def rrf_fusion(dense_hits, sparse_hits, k=60):
    scores = {}
    for rank, doc_id in enumerate(dense_hits + sparse_hits):
        scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: -x[1])
```

RRF 的 k 默认 60 是经验值，k 越小越偏向"某一路排得很靠前"的结果，k 越大越偏向"两路都稳定出现"的结果。拿 golden set 扫一遍 k ∈ {30, 60, 90} 再定，不要盲信默认值。

## 二、在线评估：LLM-as-judge 回答"答没答对"

检索指标再好看，最终用户感知的是答案质量。传统 BLEU/ROUGE 对生成式答案基本失效——同一个意思换种说法分数就崩。现在主流做法是 LLM-as-judge：让一个强模型按 rubric 给 (question, contexts, answer) 三元组打分。以 RAGAS 为例，四个核心指标各有分工：

| 指标 | 测什么 | 典型阈值 |
|---|---|---|
| context_precision | 检索到的 chunk 里有多少是相关的 | ≥ 0.7 |
| context_recall | 检索结果是否覆盖了回答所需全部信息 | ≥ 0.8 |
| faithfulness | 答案是否忠于检索内容（不幻觉） | ≥ 0.8 |
| answer_relevancy | 答案是否切题、信息完整 | ≥ 0.7 |

用法很简单，数据准备好后一次 evaluate 全出：

```python
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall
from datasets import Dataset

eval_data = Dataset.from_list([
    {
        "question": "服务降级和熔断的区别是什么？",
        "answer": "熔断是快速失败防止级联……",
        "contexts": ["<检索返回的chunk原文>", "<第二个chunk>"],
        "ground_truth": "熔断指……降级指……",
    },
    # ... 100+ 条线上真实问答
])
result = evaluate(eval_data, metrics=[faithfulness, answer_relevancy, context_precision, context_recall])
print(result)  # {'faithfulness': 0.86, 'answer_relevancy': 0.74, ...}
```

想在 CI 里当断言用，DeepEval 更顺手——它把评估做成了 pytest 风格，`assert_test` 直接抛异常让流水线红掉：

```python
from deepeval import assert_test
from deepeval.metrics import FaithfulnessMetric, ContextualPrecisionMetric

def test_rag_answer_quality():
    assert_test(
        test_case=rag_answer_case,  # input + actual_output + retrieval_context
        metrics=[FaithfulnessMetric(threshold=0.8), ContextualPrecisionMetric(threshold=0.7)],
    )
```

工具选型建议：**RAGAS 指标全、社区大，适合做评估集批量跑分；DeepEval 和 pytest 生态贴合，适合嵌 CI 断言；tonic_validate 指标少而精（retrieval_precision / augmentation_precision），适合只想盯检索-生成链路的团队**。追求严谨的离线检索对比可以直接用 BEIR 那套 15+ 数据集的 benchmark 流程，但对垂直领域 RAG 来说，自建 golden set 永远比通用 benchmark 更能反映线上问题。

## 三、踩坑记录：六个让评估结果失真的大坑

**1. 测试集泄漏。** golden set 里的文档被编进了线上索引，Hit Rate 虚高 10~20 个点。golden 文档必须从索引中排除，或者用"文档快照版本"做隔离。这是最常见的假阳性来源。

**2. judge 和生成用同一个模型。** 生成模型自己的错误倾向，judge 往往识别不出来（self-consistency 偏差）。judge 至少换一家模型，且尽量用比生成模型更强的。

**3. judge 的 rubric 不稳定。** 同一个答案换个问法分数能差 0.15。固定 prompt 模板、温度调 0、每条评估跑 3 次取中位数，能压掉大部分噪声。

**4. chunk 大小是检索质量的隐形开关。** 我这边实测：512 token 的 chunk 比 256 的 Hit Rate 高约 6 个点（信息完整），但 context_precision 低约 8 个点（混入噪声多）。没有银弹，必须拿 golden set 两个指标一起看，选 Pareto 最优。

**5. 只跑一次评估就上线。** 文档更新、embedding 模型升级都会漂移。评估集要能定期重放，把"离线评估流水线"当成和单元测试一样的东西，每次改检索配置必须过一遍。

**6. 指标全绿但线上还是差。** 大概率是评估集和线上 query 分布脱节——线上大量长尾 query 没进 golden set。解法是定期从 query 日志采样补充评估集，并监控 judge 分数的分布变化当作漂移信号。

CI 质量门禁的落地形态（GitHub Actions 示意）：

```yaml
- name: RAG retrieval quality gate
  run: python scripts/eval_rag.py --golden golden_set.jsonl
- name: Fail on regression
  run: python scripts/check_gate.py --min-hit-rate 0.80 --min-faithfulness 0.80
```

阈值建议分两层：**回归门禁**（新配置不得低于线上基线，防止改动回退）和**硬性门禁**（hit_rate ≥ 0.8、faithfulness ≥ 0.8，不达标直接 block merge）。前者比后者更重要——RAG 优化是渐进式工程，允许小幅波动，但绝不允许倒退。

## 四、总结与进阶方向

评估体系就三层：golden set 造数据 → 离线指标定检索基线 → LLM-as-judge 守生成质量，最后全部接进 CI 当门禁。工具链推荐 RAGAS + DeepEval 组合，检索对比用自建 golden set 而不是通用 benchmark。往下走有三个进阶方向：一是 GraphRAG 类结构化检索的评估（GraphRAG-Bench 有现成 benchmark 可参考）；二是 agentic retrieval（多轮工具调用式检索）的评估，传统单轮指标不够用，要引入任务完成率这类端到端指标；三是评估集自动生成 + 漂移检测，用 LLM 从线上日志半自动造 golden 数据，把评估成本从"人工标注"降到"人工审核"。
