# RAG测评系统全链路搭建指南：从检索指标到生成质量评估

RAG（检索增强生成）系统的评测一直是个老大难问题。评测指标怎么选？Pipeline 怎么搭？自动化到什么程度？本文从工程实践角度，拆解一套可落地的 RAG 测评方案。

## 一、问题拆解：RAG评测分两层

RAG 评测必须先明确一件事：**检索层和生成层是两回事，混在一起测只能得到模糊的结论。**

- **检索层（测的是什么）**：给定 query，系统能否从文档库中召回最相关的片段。衡量指标是标准 IR 指标——Hit@K、Precision@K、Recall、MRR、NDCG。
- **生成层（评的是什么）**：基于召回的上下文，LLM 生成的回答是否忠实、相关、有用。衡量指标是 Faithfulness、Answer Relevancy、Context Utilization 等。

这两层必须拆开测。一条 Fail 的用例，可能是检索没召回对内容，也可能是 LLM 没用好召回的片段。

## 二、检索层指标详解与实现

### 2.1 核心指标

| 指标 | 含义 | 适用场景 |
|------|------|----------|
| **Hit@K** | Top-K 结果是否包含相关文档 | 快速验证检索器是否有召回能力 |
| **Precision@K** | Top-K 中有多少是相关的 | 需要控制噪声回传给 LLM 时 |
| **Recall** | 所有相关文档中被召回的比例 | 评估召回覆盖率 |
| **MRR** | 第一个相关结果的倒数排名均值 | 问答场景（通常第一个片段命中最重要） |
| **NDCG** | 排序质量，考虑相关性分级 | 搜索结果排序质量评估 |

### 2.2 实现 Demo

```python
def hit_rate_at_k(questions, ground_truth, retriever, k=3):
    """计算 Hit@K"""
    hits = 0
    for q, relevant_docs in zip(questions, ground_truth):
        retrieved = retriever.retrieve(q, top_k=k)
        retrieved_ids = {doc.id for doc in retrieved}
        if set(relevant_docs) & retrieved_ids:
            hits += 1
    return hits / len(questions)


def mrr(questions, ground_truth, retriever, k=10):
    """计算 MRR (Mean Reciprocal Rank)"""
    total = 0
    for q, relevant_docs in zip(questions, ground_truth):
        retrieved = retriever.retrieve(q, top_k=k)
        for rank, doc in enumerate(retrieved, 1):
            if doc.id in relevant_docs:
                total += 1.0 / rank
                break
    return total / len(questions)


def ndcg_at_k(retrieved, relevant_scores, k=10):
    """计算 NDCG@K，支持分级相关性评分"""
    dcg = sum((2**rel - 1) / math.log2(i + 2) \
              for i, (doc, rel) in enumerate(zip(retrieved[:k], relevant_scores)))
    ideal = sorted(relevant_scores, reverse=True)[:k]
    idcg = sum((2**rel - 1) / math.log2(i + 2) for i, rel in enumerate(ideal))
    return dcg / idcg if idcg > 0 else 0.0
```

### 2.3 踩坑记录

- **Chunk 粒度的 Ground Truth**：标注时 chunk 边界不统一会导致 recall 虚高。建议统一按 256 tokens 分块后标注，或用 overlap 合并策略。
- **同义 query 的覆盖**：一条查询换个说法检索结果可能差很多。每个问题至少准备 3 个变体（专业版、口语版、简略版），取均值。
- **NDCG 需要分级标注**：很多团队只标相关/不相关，那 NDCG 退化为 DCG 排序。至少用三级：不相关(0)、部分相关(1)、完全相关(2)。

## 三、生成层评估

生成层是 LLM 输出质量评估，比检索层难得多——没有标准答案，只能靠 LLM-as-Judge 或人工标注。

### 3.1 关键指标

**Faithfulness（忠实度）**：回答中的每个陈述是否能被检索到的文档支持。这是最核心的指标——LLM 可能胡说，但 Faithfulness 能抓住。

**Answer Relevancy（回答相关性）**：回答是否回答了用户的 query。不相关 = 答非所问。

**Noise Sensitivity（噪声敏感度）**：给一段不相关上下文，LLM 是否会受影响。这测的是模型的鲁棒性。

### 3.2 LLM-as-Judge 实现

```python
from openai import OpenAI

def faithfulness_score(question, context, answer, judge_model="gpt-4o"):
    """用 LLM-as-Judge 评估忠实度"""
    prompt = f"""你是一个 RAG 评估专家。判断以下回答是否**忠实于**给定的上下文。

上下文：
{context}

用户问题：{question}

回答：{answer}

请按以下维度评分（1-5分）：
1. 回答中的每个陈述是否都在上下文中有依据？
2. 是否有事实性冲突（回答与上下文矛盾）？
3. 是否有幻觉（上下文不包含的信息但回答编造了）？

请输出 JSON：{{"faithfulness_score": int, "reasoning": str}}"""
    
    client = OpenAI()
    resp = client.chat.completions.create(
        model=judge_model,
        messages=[{"role": "user", "content": prompt}],
        response_format={"type": "json_object"},
        temperature=0
    )
    return json.loads(resp.choices[0].message.content)
```

### 3.3 指标怎么打通

RAGAS 框架提供了 Context Precision 和 Context Recall 指标，但要注意：这些是**LLM 打分的评估指标**，不是标准 IR 指标。它们用 LLM 来判断召回片段的"精确度"和"覆盖率"，本质是 Proxy Metrics——能反映问题，但不适合做精确的回归测试。

如果你想用 RAGAS 的高阶指标，一定要搭配标准 IR 指标一起看，不能只看 RAGAS 的分。

## 四、Pipeline 工程实现

### 4.1 完整的评测 Pipeline

```python
class RAGEvaluator:
    def __init__(self, retriever, llm, judge_model="gpt-4o"):
        self.retriever = retriever
        self.llm = llm
        self.judge_model = judge_model
    
    def evaluate(self, test_suite: list[dict]) -> dict:
        """test_suite: [{"question": str, "relevant_docs": [id], "context": str}]"""
        retrieval_results = []
        generation_results = []
        
        for case in test_suite:
            # 1. 检索
            retrieved = self.retriever.retrieve(case["question"], top_k=5)
            retrieved_ids = [d.id for d in retrieved]
            contexts = [d.text for d in retrieved]
            
            # 2. 检索指标
            hit = int(case["relevant_docs"][0] in retrieved_ids)
            prec = len(set(case["relevant_docs"]) & set(retrieved_ids)) / 5
            retrieval_results.append({"hit": hit, "precision": prec})
            
            # 3. 生成
            answer = self.llm.generate(case["question"], contexts)
            
            # 4. 生成指标
            faithfulness = faithfulness_score(
                case["question"], "\n".join(contexts[:3]), answer, self.judge_model
            )
            generation_results.append({"faithfulness": faithfulness})
        
        return {
            "retrieval": {
                "hit_rate": np.mean([r["hit"] for r in retrieval_results]),
                "precision": np.mean([r["precision"] for r in retrieval_results]),
            },
            "generation": {
                "avg_faithfulness": np.mean([r["faithfulness"]["faithfulness_score"] 
                                              for r in generation_results]),
            }
        }
```

### 4.2 自动化集成

建议把评测脚本做成 CI Pipeline 的一环，每次知识库更新或 LLM 模型切换时自动跑：

```yaml
# .github/workflows/rag-eval.yml
name: RAG Evaluation
on:
  schedule:
    - cron: '0 6 * * 1'  # 每周一早6点
  workflow_dispatch:
  
jobs:
  evaluate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run RAG evaluation
        run: |
          python scripts/evaluate_rag.py \
            --test-suite data/test_suite_v3.json \
            --report-dir reports/$(date +%Y%m%d)
      - name: Check regressions
        run: |
          python scripts/check_regression.py \
            --current reports/$(date +%Y%m%d)/metrics.json \
            --baseline reports/latest/metrics.json \
            --threshold 0.05
```

## 五、一些经验总结

1. **先测检索，再测生成**。90% 的 RAG 问题出在检索环节。如果 Hit@3 < 0.8，别急着调 prompt，先修 embedding 或 chunk 策略。
2. **Faithfulness 是第一生成指标**。回答可以不完整，但不能胡说。生成评测优先级：Faithfulness > Answer Relevancy > Context Utilization。
3. **基准测试用例要有"边缘 case"**。除了正常 query，必须准备：恶意/歧义 query、跨领域 query、超长 query（>500 tokens）——这些才是暴露系统缺口的有效用例。
4. **LLM-as-Judge 不是圣杯**。开源的 Judge 模型（如 Prometheus、Auto-J）在中文场景下表现参差不齐。如果预算允许，用 GPT-4o 做 Judge；否则至少做 20% 的人工抽检校准。
5. **不要混用指标**。标准 IR 指标（Hit/Precision/Recall）和 RAGAS 的高阶指标是两套体系，前者衡量检索器本身，后者用 LLM 打分做整体评估。混在一起看会得出矛盾的结论。

最后推荐去看一下 RAGAS 框架的源码（github.com/explodinggradients/ragas），它的指标实现逻辑比文档写得清楚。了解它的评估策略后，再决定要不要完全引用它的指标，还是只参考思路自己搭。
