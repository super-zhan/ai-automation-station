# Mobilewright：用 Playwright 的体验写移动端自动化测试

如果你写过 Web 端的 E2E 测试，大概率用过 Playwright。它的 auto-waiting、链式定位器、语义化 `getByRole` 让人回不去 Selenium。

现在移动端也有对标方案了：**Mobilewright**（https://github.com/mobile-next/mobilewright）—— 一个基于 Playwright 架构思想构建的跨平台移动自动化框架，2026 年 3 月发布，目前 300+ Star，Apache 2.0 协议。

它的核心理念很简单：**把 Playwright 的开发者体验搬到 iOS/Android 上**。

## 为什么不是 Appium / Detox / XCTest？

当前移动测试生态的问题很明显：

| | Appium | Detox | XCTest/Espresso | Mobilewright |
|---|---|---|---|---|
| API 风格 | Selenium (WebDriver) | 自定义 | 原生框架专属 | Playwright (`getByRole`, `expect`) |
| Auto-waiting | 手动 sleep/wait | 部分自动 | 手动 | 内置，每个操作自动等待 |
| 安装配置 | 服务端+驱动+Caps | React Native 专用 | Xcode/AS 独占 | `npm install mobilewright` |
| 跨平台 | 是（但配置冗长） | RN 限定 | 单平台 | iOS+Android 统一 API |
| AI Agent 支持 | 有限 | 不支持 | 不支持 | **一等公民**（无障碍树驱动） |
| 定位器 | XPath, CSS, ID | Test ID | 原生查询 | 语义角色+标签+正则 |

Appium 最大的问题是 WebDriver 协议天生对移动端不友好——你写 `driver.findElement(By.xpath("//XCUIElementTypeButton[@name='Sign In']"))`，慢、脆弱、维护成本高。Detox 只认 React Native，覆盖率太窄。原生 XCTest/Espresso 快但写两套代码。

Mobilewright 的做法：用 Playwright 的 **`getByRole`/`getByLabel`/`getByText`** 语义定位器 + 内置 auto-waiting + 跨平台统一接口。如果你写过 Playwright，上手成本几乎为零。

## 快速上手：30 秒跑通第一个测试

```typescript
import { ios, expect } from 'mobilewright';

const device = await ios.launch({ bundleId: 'com.example.myapp' });
const { screen } = device;

await screen.getByLabel('Email').fill('user@example.com');
await screen.getByLabel('Password').fill('password123');
await screen.getByRole('button', { name: 'Sign In' }).tap();

await expect(screen.getByText('Welcome back')).toBeVisible();

await device.close();
```

不需要启动 Appium Server，不需要配置 Desired Capabilities，不需要在代码里写 `Thread.sleep()`。`ios.launch()` 自动检测已启动的模拟器，自动启动 mobilecli 守护进程，测试结束自动清理。

### 环境检查

```bash
npx mobilewright doctor
```

输出了什么？它会检查 Xcode、Android SDK、ADB、模拟器列表，告诉你缺什么以及怎么装。

## 架构设计：为什么能"像 Playwright 一样"

Mobilewright 的架构分三层：

```
┌─────────────────────────────────────┐
│  User-facing API                     │
│  (Locator, Screen, Expect assertions)│
├─────────────────────────────────────┤
│  @mobilewright/core                  │
│  (Device, Screen, Locator, expect)   │
├─────────────────────────────────────┤
│  Driver Layer                        │
│  @mobilewright/driver-mobilecli      │
│  (WebSocket JSON-RPC ↔ mobilecli)   │
├─────────────────────────────────────┤
│  mobilecli (on-device agent)         │
│  (iOS: XCUITest, Android: UiAutomator)│
└─────────────────────────────────────┘
```

关键设计决策：

**1. 不使用 WebDriver 协议**。Appium 选择 WebDriver 是为了复用 Selenium 生态，但这个协议本身是按浏览器设计的——session、window handle、element reference 的模型对移动端很别扭。Mobilewright 用 **WebSocket JSON-RPC** 直连设备上的 mobilecli agent，每个请求对应一个移动端原生操作，延迟更低。

**2. 定位器不依赖 XPath**。Playwright 用户知道，`getByRole` 比 `//button[@name="Sign In"]` 快了一个数量级（因为直接走 accessibility tree，不需要 DOM 遍历）。Mobilewright 把同样的思路搬到移动端：通过 mobilecli 获取设备的无障碍树（accessibility tree），然后在这些节点上做语义匹配。

**3. Auto-waiting 引擎**。每个操作（tap, fill, swipe）触发前会轮询无障碍树，直到目标元素 visible + enabled + bounds stable。放弃了对 WebDriver 的 `ExpectedConditions` 的依赖，也避免了 `Thread.sleep()`。

## 定位器系统深度解析

这是 Mobilewright 最值得讲的部分。来看它的定位器 API 家族：

```typescript
// 语义角色（推荐）
screen.getByRole('button', { name: 'Sign In' })

// 无障碍标签
screen.getByLabel('Email')

// 显式文本
screen.getByText('Welcome')
screen.getByText(/welcome/i)
screen.getByText('welcome', { exact: false })

// 元素类型
screen.getByType('TextField')

// 占位符
screen.getByPlaceholder('Search...')

// 测试 ID（最稳定）
screen.getByTestId('login-button')
```

每个定位器都是**惰性求值**的——不立即查询，只在执行操作或断言时触发查询。这跟 Playwright 的 Locator 模型完全一致。

### 链式组合和过滤

```typescript
// 在第一个 Cell 里找 Delete 按钮
const row = screen.getByType('Cell');
await row.getByRole('button', { name: 'Delete' }).tap();

// 多元素过滤
screen.filter({ hasText: 'In stock' })
screen.filter({ hasNot: screen.getByText('Ad') })

// 逻辑组合
locator.and(screen.getByRole('button'))
locator.or(screen.getByText('Retry'))

// 多选处理
locator.first()
locator.last()
locator.nth(2)
await locator.count()
```

### 角色映射机制（iOS ↔ Android）

一个值得关注的细节：`getByRole` 是如何跨平台工作的？

```typescript
// 你写这一行：
screen.getByRole('button', { name: 'Sign In' })

// iOS 上匹配：Button, ImageButton
// Android 上匹配：Button, ImageButton, ReactViewGroup(clickable=true)
```

框架维护了一张角色映射表。例如 `button` 角色在 iOS 上匹配 `XCUIElementTypeButton`（或 SwiftUI 的 Button），在 Android 上匹配 `android.widget.Button` + `ImageButton` + 带 clickable 属性的 `ReactViewGroup`（避免 React Native 的假阳性）。

## 断言系统：轮询等待，不用 setInterval

```typescript
await expect(locator).toBeVisible();
await expect(locator).not.toBeVisible();
await expect(locator).toBeEnabled();
await expect(locator).toHaveText('Welcome back!');
await expect(locator).toHaveText(/welcome/i);
await expect(locator).toContainText('back');
await expect(locator).toHaveValue('user@example.com');
await expect(locator).toHaveCount(3);

// 自定义超时
await expect(locator).toBeVisible({ timeout: 10_000 });
```

所有断言默认轮询 5 秒直到满足或超时。`expect(locator).not.toBeVisible()` 等效于 `waitFor({ state: 'hidden' })`。不需要手动写 `try/catch + Thread.sleep` 组合。

## WebView 混合应用测试

混合应用（Cordova/Capacitor/Ionic/WKWebView）在移动测试里一直是难点。Appium 的 context 切换是经典的坑——经常切不过去，或者切过去找不到元素。

Mobilewright 提供了一个优雅的解决方案：

```typescript
// 获取 WebView 并拿到 Playwright 兼容的 Page
const webview = screen.getByWebView();
const page = await webview.page();

// 之后就是标准 Playwright API
await page.goto('https://example.com/login');
await page.getByLabel('Email').fill('user@example.com');
await page.getByRole('button', { name: 'Sign In' }).click();

await expect(page).toHaveURL(/dashboard/);
```

它通过无障碍树定位到 WebView 节点，然后通过 mobilecli 的 WebView 调试协议桥接出一层 Playwright-compatible Page。web 内容的定位器和操作接口和 Playwright 完全一致。

## 与 Playwright Test 集成

Mobilewright 不是和 Playwright Test 竞争，而是扩展它：

```typescript
import { test, expect } from '@mobilewright/test';

test.use({
  bundleId: 'com.example.myapp',
  video: 'retain-on-failure',
  viewTree: 'on-failure',
});

test('can sign in', async ({ device, screen, bundleId }) => {
  await device.terminateApp(bundleId).catch(() => {});
  await device.launchApp(bundleId);

  await screen.getByLabel('Email').fill('user@example.com');
  await screen.getByLabel('Password').fill('password123');
  await screen.getByRole('button', { name: 'Sign In' }).tap();

  await expect(screen.getByText('Welcome back')).toBeVisible();
});
```

- `device` fixture 按 worker 维度共享连接，测试结束后自动 `device.close()`
- `screen` fixture 提供 `device.screen`，失败时自动截图
- 支持 `video: 'retain-on-failure'` 录制回放
- 支持 `viewTree: 'on-failure'` 在失败时附加无障碍树 JSON

```bash

# 设备管理
npx mobilewright devices             # 列出所有设备/模拟器

# 调试

npx mobilewright screenshot          # 截图

# 运行测试
npx mobilewright test                # 跑全部测试
npx mobilewright test login.test.ts  # 指定文件
npx mobilewright test --grep "sign"  # 按名称过滤
npx mobilewright test --workers 4    # 并行 worker 数
npx mobilewright test --retries 2    # 失败重试
npx mobilewright test --reporter html

# CI 支持
npx mobilewright merge-reports ./blob-reports  # 合并分片报告
```

## AI Agent 支持

Mobilewright 将自己定位为"AI agent 时代的移动测试框架"。这个判断成立的原因是：

传统的移动自动化（Appium/Detox）依赖视觉定位（截图+坐标）或 DOM 结构的 XPath，这两种方式对 AI agent 都不友好——视觉方案 token 消耗大、坐标不稳定、XPath 脆弱。

Mobilewright 直接暴露设备的**无障碍树（accessibility tree）**作为与 AI 交互的接口。这是一份结构化的 JSON，包含所有元素的角色、标签、状态、位置和层级关系。AI agent 不需要视觉模型，直接读取这棵树的语义信息，就能做出精确的操作决策。

```typescript
// AI agent 控制手机——读无障碍树，执行语义操作
await screen.getByRole('button', { name: 'Sign In' }).tap();
await screen.getByLabel('Email').fill('user@example.com');
await expect(screen.getByText('Welcome')).toBeVisible();
```

和 `mobile-mcp`（独立的 MCP server）配合使用，可以让 Claude、Cursor 等 AI 工具直接操控移动设备。

## 框架支持矩阵

| 框架 | iOS | Android | 说明 |
|---|---|---|---|
| UIKit / Storyboards | ✅ | — | 完整的原生元素类型 |
| SwiftUI | ✅ | — | 映射到标准 XCUIElementType 无障碍树 |
| Jetpack Compose | — | ✅ | 渲染为原生 Android 无障碍节点 |
| Android Views (XML) | — | ✅ | 完整原生支持 |
| React Native | ✅ | ✅ | RN 类型映射到角色 |
| Expo | ✅ | ✅ | 同上（Expo 编译为 RN） |
| .NET MAUI | ✅ | ✅ | 编译为原生控件 |
| Cordova / Capacitor | ✅ | ✅ | WebView 内容通过无障碍树访问 |
| Flutter | ⏳ | ⏳ | Skia 渲染，需要 Dart VM Service 驱动 |

## 值得关注的几个踩坑点

1. **React Native 的假阳性问题**：RN 中所有容器视图都是 `ReactViewGroup`，如果不加 `clickable=true` 或 `accessible=true`，Mobilewright 不会将其匹配为 button 角色。开发时如果遇到定位不到元素，先检查元素属性。

2. **链式定位的边界判定**：Mobilewright 的链式定位基于 bounds containment（父元素的矩形框包含子元素的矩形框）。这在 flat list 结构的无障碍树中是正确的，但如果父元素设置了 `clipToBounds=false`，子元素可能超出父元素视觉边界，此时框架使用无障碍树中的层级关系而非坐标关系做判断。

3. **WebView 桥接延迟**：`screen.getByWebView().page()` 返回的 Page 对象与 Playwright 的 Page 接口一致，但底层走的是 WebSocket，首次导航可能比纯 Playwright 慢 1-2 秒。建议在测试中适当增大 `actionTimeout`。

## 总结

Mobilewright 解决了移动端自动化测试长期存在的几个痛点：配置复杂（无需 Appium Server）、定位器脆弱（语义定位替代 XPath）、跨平台重复工作（统一 API）。技术选型上，它赌对了三个方向：

- **Playwright API 风格**是当前开发者体验最好的浏览器自动化方案，复制到移动端是聪明的选择
- **无障碍树而非视觉/坐标**的方案，恰好契合了 AI agent 时代的交互范式
- **WebSocket JSON-RPC 替换 WebDriver**，协议层面更轻量、更适移动端

**进阶方向**：Flutter/Compose Multiplatform 支持一旦落地，Mobilewright 将成为真正意义上覆盖全移动技术栈的统一测试框架。同时，它在云测设备矩阵和 CI 分片的成熟度上还有提升空间，值得持续关注。

如果你已经在 Web 端用 Playwright，移动端引入 Mobilewright 的学习成本几乎为零。试试在下一个移动项目里跑 `npx mobilewright init`。
