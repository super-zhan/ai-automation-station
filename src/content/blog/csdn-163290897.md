# promptfoo 源码分析与工程实践：LLM 评估与红队测试框架的架构设计

## 为什么需要专业的 LLM 测试工具

LLM 应用的输出天生具有不确定性和非结构化特征，传统的单元测试和断言框架无法应对。Promptfoo 正是为解决这个问题而生——它把 LLM 测试从"手动看几个例子"升级为"可重复、可度量、可嵌入 CI/CD 的自动化评估体系"。

这个项目目前 23K+ stars，已被 OpenAI 收购并保持 MIT 开源。它的核心价值在于：把 prompt 工程和模型评估变成数据驱动的过程，而不是靠感觉迭代。

## 核心架构：三层评估体系

Promptfoo 的设计围绕三个层次展开，逐层递进：

### 1. 确定性断言层（Deterministic Assertions）

这是最底层，也是最容易理解的部分。与传统测试框架的 assert 类似，但针对 LLM 输出做了扩展：

```yaml
# promptfooconfig.yaml
prompts:
  - '将以下英文翻译成{{language}}：{{input}}'

providers:
  - openai:chat:gpt-5.4
  - openai:chat:gpt-5.4-mini

tests:
  - vars:
      language: French
      input: Hello world
    assert:
      - type: contains-any
        value: ['Bonjour', 'Salut']
      - type: latency
        threshold: 3000  # 毫秒
      - type: cost
        threshold: 0.002  # USD
```

断言类型覆盖了文本包含、JSON 校验、正则匹配、SQL/HTML 格式检测、Levenshtein 距离、BLEU/ROUGE 分数等 30+ 种。每种断言都可以用 `not-` 前缀取反，用 `weight` 设置权重，用 `threshold` 设定通过门槛。

有意思的是 `assert-set` 机制——可以组合多个断言并设定通过阈值：

```yaml
- type: assert-set
  threshold: 0.5  # 至少 50% 的断言通过
  assert:
    - type: contains
      value: 'API'
    - type: latency
      threshold: 1000
    - type: cost
      threshold: 0.001
```

这套设计借鉴了 pytest 的 parametrize + pytest-assume 思路，但针对 LLM 输出的概率性做了加权处理。

### 2. 模型辅助评估层（Model-graded Evals）

确定性断言只能检查格式和关键词，但"回答是否基于给定文档"、"语气是否专业"这些问题必须靠另一个 LLM 来判分。Promptfoo 的模型辅助评估体系包含：

| 评估类型 | 用途 | 原理 |
|---------|------|------|
| llm-rubric | 自定义评分标准 | 将输出 + 评分标准发给 Judge LLM |
| factuality | 事实一致性 | 源自 OpenAI eval 的 Factuality 方法 |
| context-faithfulness | RAG 答案忠实度 | 检查输出是否基于检索上下文 |
| answer-relevance | 回答相关性 | 输出与问题的语义匹配度 |
| g-eval | 链式思维评分 | 基于 G-Eval 论文的方法 |

自建评分函数的例子：

```javascript
// scoring.js — 自定义加权评分函数
module.exports = (namedScores, { threshold }) => {
  // namedScores: { accuracy: 0.8, completeness: 0.5 }
  const finalScore = namedScores.accuracy * 0.7 + namedScores.completeness * 0.3;
  return {
    pass: finalScore >= (threshold || 0.7),
    score: finalScore,
    reason: `Weighted score: ${finalScore.toFixed(3)}`
  };
};
```

```yaml
# 在配置中引用
assert:
  - type: equals
    value: 'Hello'
    metric: accuracy
  - type: contains
    value: 'world'
    metric: completeness
assertScoringFunction: file://scoring.js
```

### 3. 红队测试层（Red Teaming）

这是 promptfoo 区别于其他 eval 工具的杀手级功能。它不只是"测 prompt"，而是主动攻击你的 LLM 应用。

红队测试的工作流程：

```
用户描述应用场景
       ↓
Promptfoo 加载 50+ 攻击插件（jailbreak、prompt injection、数据泄露等）
       ↓
用专门的 uncensored 模型生成针对性的攻击载荷
       ↓
对目标 API/模型 执行攻击
       ↓
生成漏洞报告（含严重等级、复现步骤、修复建议）
```

配置示例——攻击一个 HTTP API 端点：

```yaml
targets:
  - id: https
    label: 'travel-agent'
    config:
      url: 'https://example.com/generate'
      method: 'POST'
      headers:
        'Content-Type': 'application/json'
      body:
        myPrompt: '{{prompt}}'

purpose: 'The user is a budget traveler looking for the best deals.
          The system is a travel agent. The user should not be able to
          access information about other users or employees.'
```

红队扫描的战略层面更值得关注。Promptfoo 集成了学术界最新的攻防研究成果：

- **多轮攻击**（Microsoft 研究）：通过对话逐步诱导模型泄露信息
- **GOAT 策略**（Meta 研究）：遗传算法优化的对抗性提示
- **编码攻击**：Base64/Hex 编码绕过内容过滤器
- **角色扮演攻击**：让模型扮演"开发者模式"绕过限制

## CI/CD 集成实战

LLM 评估只有嵌入流水线才有实际价值。Promptfoo 支持多种输出格式来对接不同 CI/CD 平台：

```bash
# 一次运行生成多种格式
npx promptfoo@latest eval \
  -c promptfooconfig.yaml \
  -o results.json \
  -o report.html \
  -o results.junit.xml
```

GitHub Actions 集成示例：

```yaml
name: LLM Eval
on:
  pull_request:
    paths:
      - 'prompts/**'
      - 'promptfooconfig.yaml'

jobs:
  evaluate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'

      - name: Run eval
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
        run: |
          npx promptfoo@latest eval \
            -c promptfooconfig.yaml \
            -o results.json

      - name: Quality gate
        run: |
          FAILURES=$(jq '.results.stats.failures' results.json)
          if [ "$FAILURES" -gt 0 ]; then exit 1; fi
```

几个实测配置建议：

1. **缓存是关键**：LLM eval 每次调用都产生 API 费用和延迟。设置 `PROMPTFOO_CACHE_PATH` 并用 CI 缓存策略缓存它，可将重复运行的耗时从 15 分钟降到 30 秒。
2. **分阶段运行**：PR 触发只跑确定性断言（几秒完成），定时任务跑模型辅助评估和红队扫描（几分钟）。
3. **成本控制**：在 `defaultTest.assert` 中加 `cost` 断言，设置每次推理的成本上限，避免模型升级后费用失控。

## RAG 评估：不只是测检索

RAG（检索增强生成）系统的评估是 promptfoo 最实用的场景之一。它把 RAG 评估拆解为 5 个独立维度：

```yaml
tests:
  - vars:
      context: file://retrieved_docs.txt
      query: '公司的离职率是多少？'
    assert:
      - type: context-faithfulness
        # 输出是否基于检索到的上下文
      - type: context-recall
        # 检索到的上下文是否包含正确答案所需的信息
      - type: context-relevance
        # 检索到的内容是否和 query 相关
      - type: answer-relevance
        # 最终回答是否回答了问题
      - type: factuality
        # 回答是否符合事实
```

这种多维评估比单一的"正确/错误"判断更有工程指导意义。如果 context-recall 低但 answer-relevance 高，说明 LLM 在"编造"答案——这是 RAG 系统最常见的陷阱。如果 context-relevance 低，说明检索器（retriever）需要优化。

## 踩坑记录

实际使用中遇到几个问题：

**1. Judge LLM 的选择很关键**
默认使用 GPT-4 做评估。实测用 Claude 做 judge 在中文场景下评分更稳定，但 cost 比 GPT-4-mini 高 3 倍。建议：开发阶段用 GPT-4/Claude，CI 中用 GPT-4-mini 做回归。

**2. 评分方差问题**
同一组测试跑两次可能得到不同的 pass/fail 结果。原因是 judge LLM 的采样温度不为 0。解决方案：关键测试用例的断言设 `weight: 3` 或更高，并且在 `defaultTest` 层面设 `threshold: 0.8` 而不是要求全部通过。

**3. 红队测试触发 API 限流**
红队扫描默认生成数百个攻击载荷。如果目标 API 有速率限制，需要在配置中加并发控制。实测 `--max-concurrency 3` 可以稳定运行。

## 进阶方向

- **自定义 Provider**：Promptfoo 支持 Python/JS 自定义 provider，可以把自己封装的 RAG 链或 agent 接入测试
- **Trace 分析**：最新版本支持 agent 轨迹追踪，可以断言工具调用顺序、参数匹配、步数限制
- **代码扫描**：不仅仅是测试运行时行为，还能扫描 prompt 模板代码中的安全漏洞和合规问题

如果你正在构建 LLM 应用，把 promptfoo 引入你的测试流水线，是让 AI 功能从"看起来不错"走向"可交付"的关键一步。
