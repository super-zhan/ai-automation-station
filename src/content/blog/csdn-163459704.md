# LLM 测试框架 promptfoo：把 prompt 评测变成可回归的 CI 用例

LLM 应用测试和传统测试有一个根本差异：没有 oracle。传统断言是"输出 === 期望值"，而 LLM 输出是概率采样，同一个 prompt 跑两次结果就不同，期望值根本写不出来。promptfoo（GitHub 23.9k stars，MIT，npm 版本 0.121.x，Node >= 22.22，已被 OpenAI 收入麾下但仍保持开源）解决这个问题的方式很直接：把评测声明成 YAML 配置——prompts、providers、tests 三个维度组成笛卡尔积矩阵，跑完用断言自动判定，结果进 CI 当回归用例。本文拆解它的配置模型、断言体系（确定性 vs 模型辅助）、RAG 评测和红队能力，以及落地时最实际的成本与稳定性问题。

## 核心抽象：prompts × providers × tests 矩阵

promptfoo 的配置文件就一个 `promptfoo.yaml`，核心是三个字段的笛卡尔积：

```yaml
prompts:
  - file://prompt1.txt        # 也可以直接写字符串
  - file://prompt2.txt
providers:
  - openai:gpt-5-mini
  - vertex:gemini-2.0-flash-exp
tests:
  - vars:
      language: French
      input: Hello world
    assert:
      - type: contains-json
      - type: javascript
        value: output.toLowerCase().includes('bonjour')
  - vars:
      language: German
      input: How's it going?
    assert:
      - type: similar
        value: was geht
        threshold: 0.6   # 嵌入向量余弦相似度
```

`promptfoo eval` 会展开成 2 prompts × 2 providers × 2 tests = 8 次模型调用，生成一个矩阵视图（prompt 行 × provider 列 × test case 格）；`promptfoo view` 起本地 web UI 看结果和 diff。`promptfoo eval --share` 可以生成一个只读分享链接给团队评审。

这个矩阵设计是整个工具的基石：prompt 版本迭代时，你看到的不再是"我试了一下感觉变好了"，而是每一个 prompt × provider × test 组合的通过/失败明细。prompt 改动导致某个 corner case 劣化，在矩阵里一目了然。

## 执行管线与 Provider 抽象

eval 的一次运行是条清晰的管线：解析 YAML → 展开笛卡尔积生成任务队列 → 按并发度执行模型调用（带缓存命中检查）→ 跑断言 → 写结果库并生成报告。任务之间无依赖，天然可并行；每个任务的结果按 prompt + provider + vars 的哈希落盘缓存，命中直接跳过模型调用。理解这条管线对排查"为什么这次 eval 这么快/这么慢"很有用——慢在模型调用还是慢在 judge 断言，一眼就能分开。

Provider 层是另一个值得借鉴的抽象。配置里 `openai:`、`anthropic:`、`vertex:`、`azure:`、`bedrock:`、`ollama:` 这些前缀只是统一接口的适配器，真正的 Provider 协议只有"输入 prompt 和 vars，输出文本/JSON"这么简单，所以自定义 provider 非常轻：

```python
# custom_provider.py —— 接入公司内部网关或任意本地服务
def call_api(prompt, context, **kwargs):
    # 任何逻辑：转发内部模型网关、查缓存、走灰度
    return {"output": gateway.infer(prompt), "cost": 0.001}
```

本地模型场景（Ollama、vLLM 起的内网模型）直接 `ollama:llama3.1` 就能跑，prompt 和测试数据完全不出机器——对数据合规要求高的团队，这是把评测做进日常流程的前提。实际收益是：评测脚本写一次，换模型就是改一行 provider 前缀，模型选型对比（同一批测试用例跑 GPT 系 vs 开源系）从"各自写脚本"变成"同一套用例直接出矩阵"。

## 断言体系：确定性 vs 模型辅助

断言是自动判定输出的核心，promptfoo 把它们分成两类：

| 类别 | 典型类型 | 判定机制 | 额外成本 |
|---|---|---|---|
| 确定性 | `contains` / `regex` / `is-json` / `contains-json` / `javascript` / `python` / `latency` / `cost` / `bleu` / `rouge-n` / `is-valid-function-call` | 本地程序化检查 | 0（纯计算） |
| 模型辅助 | `similar` / `llm-rubric` / `g-eval` / `factuality` / `answer-relevance` / `context-faithfulness` / `context-recall` / `context-relevance` / `classifier` / `moderation` | 嵌入相似度或 LLM judge 打分 | 每次断言多一次模型调用 |

设计上有个细节值得抄：**所有断言都可以加 `not-` 前缀取反**（`not-equals`、`not-regex`），并且支持 `weight` 加权——比如 `is-json` 权重 2、`similar` 权重 1，按加权得分判定整体通过率。这解决了"多个断言有轻重"的实际问题。

模型辅助断言里，`similar` 走嵌入向量余弦相似度，适合语义等价判断；`llm-rubric` 和 `g-eval` 则是让一个 LLM 当 judge 按你写的评分标准打分，`g-eval` 还带 chain-of-thought 推理过程，稳定性明显好于直接打分。函数断言（`javascript` / `python`）最灵活，能写任意校验逻辑，相当于把单测里的断言函数搬进 eval 配置：

```yaml
- type: python
  value: |
    import json
    data = json.loads(output)
    assert data["status"] in ("ok", "retry")
    assert 0 <= data["score"] <= 100
```

## RAG 评测：四个 context 系断言

RAG 应用是 LLM 测试里最典型的场景，因为它的失败模式可以拆解：检索错了、上下文没用到、回答了但没依据。promptfoo 为此提供了四个配套断言，分别锁一个环节：

```yaml
tests:
  - vars:
      question: 你们的退款政策是什么？
      context: |
        退货政策：购买后 30 天内可申请全额退款，需保留原始包装。
        数码产品拆封后仅支持换货。
    assert:
      - type: context-relevance    # 检索到的 context 是否与问题相关
      - type: context-recall       # 正确答案是否真的在 context 里（召回）
      - type: context-faithfulness # 输出是否忠于 context，没编造
      - type: answer-relevance     # 输出是否回答了问题
```

四者全绿才说明链路是通的：检索到了对的文档、文档里有答案、模型用了且没幻觉。任何一个红了，根据是哪个断言就能直接定位到检索层还是生成层的问题，不用再对着一个"看起来不太对"的回答瞎猜。这套组合拳就是 RAG 评测的标配，比单独看"回答对不对"信息量大得多。

## 红队：把安全测试也声明化

promptfoo 的 red team 模式把渗透测试也变成了配置：`promptfoo redteam` 会按插件（prompt injection、jailbreak、PII 泄露、越狱变体等）自动生成攻击用例批量打你的应用，支持白盒（提供提示词模板）和黑盒（只给 API 端点）两种模式，产出带漏洞等级的安全报告。这对生产环境的 LLM 应用基本是必须的——prompt injection 不是"可能发生的风险"，而是"一定会被扫到的问题"，Discord 的 Clyde AI 等案例都是上线后被社区找出注入漏洞。

## 落地踩坑记录

**1. 矩阵爆炸 = 账单爆炸。** 3 个 prompt × 4 个 provider × 50 个 test case 就是 600 次调用，如果再加 model-graded 断言，每个断言又是一次 judge 调用，直接翻倍。控制手段：先用小矩阵（1 prompt × 1 provider）把断言调对，再扩维度；用 `--max-concurrency` 限制并发避免触发 provider 限流；CI 里拆 nightly 全量跑、PR 只跑 smoke 集。

**2. 缓存是省钱的关键。** promptfoo 默认按 prompt + provider + vars 的哈希缓存结果，改了一个 prompt 只重跑受影响的分支。要利用好这一点：把不变的部分（provider、vars）和经常改的部分（prompt 文本）分开管理，改动范围越小，缓存命中率越高。

**3. 阈值别拍脑袋。** `similar` 的 `threshold` 默认 0.6 起调，建议先跑一遍真实数据集看分数分布再定阈值，否则要么全红要么全绿。`latency` / `cost` 断言同理，先量化基线再设阈值。

**4. judge 模型的选择直接影响结果稳定性。** 用弱模型当 judge，评分方差大，一次改 prompt 可能因为 judge 抖动误报回归；固定同一个 judge 模型（不要今天 gpt-5-mini 明天换别的），否则"分数变化"里混入了 judge 变化。对非确定性，用 `repeats` 让同一用例跑 N 次看通过率，而不是单次结果下结论。

**5. CI 集成。** `promptfoo eval --ci` 输出机器可读结果，`--threshold 0.9` 低于通过率即非零退出，配 GitHub Action 或任意 CI 的失败拦截就能把 prompt 回归挡在合并前。这一步做完，"prompt 改动导致线上劣化"才真正从口头约定变成工程约束：

```yaml
# .github/workflows/llm-eval.yml
name: llm-eval
on:
  pull_request:
    paths: ['prompts/**', 'promptfoo.yaml']
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g promptfoo
      - run: promptfoo eval --ci --threshold 0.9
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
```

`paths` 过滤很关键：只有 prompt 或配置变更才触发评测，避免每次 PR 都烧一遍模型调用费。

## 总结与进阶方向

promptfoo 的价值不在"测 LLM"这个口号，而在把不可判定的 LLM 输出工程化成可回归的声明式测试：矩阵展开 + 双轨断言 + CI 阈值。进阶可以看三条线：`g-eval` 自定义评分标准（比 llm-rubric 更稳）、`select-best` 多输出择优（适合 prompt 调优阶段）、`trajectory:*` 系列断言（`trajectory:tool-used`、`trajectory:tool-sequence`）——agent 应用的评测正在从"看最终回答"走向"校验工具调用轨迹"，这会是 LLM 测试下一个主战场。
