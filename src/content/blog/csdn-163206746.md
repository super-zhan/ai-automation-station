# LLM评估实战：用Evidently AI 构建生产级测试流水线

## 痛点：LLM上线后，凭什么说"靠谱"？

传统软件测试有明确的断言——状态码200、JSON Schema校验、响应时间<200ms。但LLM应用的输出是自然语言，没有确定性的"正确"答案。同一个prompt给GPT-4和Claude，产出风格迥异；同一个模型同一prompt，两次调用也可能跑偏。

更棘手的是：**回归测试怎么做？** 代码改了，prompt template调整了，RAG知识库更新了，怎么知道LLM输出质量没掉？靠人工看？不可扩展。靠BLEU/ROUGE？对创意生成类任务基本失效。

Evidently AI（GitHub 7700+ stars）提供了一个工程化的解决方案：把LLM评估从"凭感觉"变成"可计量、可断言、可集成进CI"。它的核心设计理念是——评估和测试LLM输出应该像写pytest测试一样自然。

## 架构拆解：Evidently 的评估矩阵

Evidently 的 LLM 评估模块围绕三个层次展开：

```
┌─────────────────────────────────────────────┐
│              Evaluator Suite                  │
│  ┌──────────┐ ┌──────────┐ ┌───────────────┐  │
│  │ Text Evals│ │  Pairwise│ │  LLM-as-Judge │  │
│  │  · 毒性    │ │  · A/B   │ │  · 相关性      │  │
│  │  · 偏见    │ │  · 偏好   │ │  · 事实一致性   │  │
│  │  · PII    │ │  · 排名   │ │  · 安全性      │  │
│  └──────────┘ └──────────┘ └───────────────┘  │
├─────────────────────────────────────────────┤
│             Metrics Engine                    │
│  PresetMetrics · CustomMetrics · Composite    │
├─────────────────────────────────────────────┤
│          Test Suite (pytest-style)            │
│  assert metric.value >= threshold             │
│  assert metric.fail_count == 0               │
├─────────────────────────────────────────────┤
│          Report / Dashboard                   │
│  JSON · HTML · Colab · DataFrames             │
└─────────────────────────────────────────────┘
```

这层抽象的意义在于：**评估逻辑和业务逻辑解耦**。你的LLM应用只管产出一份标准格式的`EvaluationResult`，剩下的打分、统计、阈值判断、可视化全部由框架接管。

## 实战：给RAG问答系统写评估

### 1. 安装并初始化

```bash
pip install evidently evidently[llm]
```

Evidently 的 LLM 模块需要接入一个评判模型（judge LLM），用来评估输出质量。可以用GPT-4、Claude、或者本地部署的开源模型。

```python
import evidently
from evidently.ui.workspace import Workspace
from evidently.metric_preset import TextEvalPreset
from evidently.test_suite import TestSuite
from evidently.tests import TestMetricValue, TestShareOfFailed

# 配置评判模型（这里用OpenAI兼容接口）
from evidently.llm.judge import LLMJudge

judge = LLMJudge(
    provider="openai",
    model="gpt-4o-mini",  # 生产环境建议gpt-4o
    api_key=os.getenv("OPENAI_API_KEY"),
    # 也支持本地模型：
    # provider="openai", api_base="http://localhost:1234/v1", model="qwen2.5-7b-instruct"
)
```

### 2. 定义评估场景

假设我们有一个客服问答RAG系统，需要评估三个方面：**答案相关性（Answer Relevance）、事实一致性（Faithfulness）、有害内容（Harmfulness）**。

```python
from evidently.metrics import (
    LLMAnswerRelevance,
    LLMFaithfulness,
    LLMHarmfulness,
)

# 构造测试数据：每个样本包含 question, answer, context
test_cases = [
    {
        "question": "如何退款？",
        "answer": "您可以在订单页点击退款按钮，系统会在3个工作日内处理。",
        "context": "退款政策：用户可在下单后30天内申请退款，处理周期3-5个工作日。"
    },
    {
        "question": "你们服务器是不是又挂了？",
        "answer": "目前系统运行正常，您可以尝试刷新页面。如果仍有问题，请联系技术支持。",
        "context": "系统状态页面显示所有服务正常运行。"
    },
    {
        "question": "密码忘了怎么办？",
        "answer": "点击登录页的'忘记密码'，通过注册邮箱重置。",
        "context": "密码重置流程：用户可通过邮箱或短信验证码重置密码。"
    },
]

# 批量评估
results = []
for case in test_cases:
    eval_result = judge.evaluate(
        metrics=[
            LLMAnswerRelevance(),
            LLMFaithfulness(),
            LLMHarmfulness(),
        ],
        **case,
    )
    results.append(eval_result)
    print(f"Q: {case['question'][:30]}... "
          f"Rel: {eval_result['LLMAnswerRelevance']:.2f} "
          f"Faith: {eval_result['LLMFaithfulness']:.2f} "
          f"Harm: {eval_result['LLMHarmfulness']:.2f}")
```

输出示例：

```
Q: 如何退款？...              Rel: 0.92  Faith: 0.88  Harm: 0.01
Q: 你们服务器是不是又挂了？...   Rel: 0.78  Faith: 0.95  Harm: 0.02
Q: 密码忘了怎么办？...          Rel: 0.95  Faith: 0.90  Harm: 0.00
```

### 3. 断言式测试（pytest风格）

这才是真正和CI/CD集成的核心。Evidently TestSuite 允许你像写单元测试一样写LLM评估：

```python
from evidently.test_suite import TestSuite
from evidently.tests import TestMetricValue, TestShareOfFailed

# 把上面结果收集成 Dataset
from evidently.core import Dataset

dataset = Dataset.from_list(results)

suite = TestSuite(
    tests=[
        # 每个样本的答案相关性不低于0.7
        TestMetricValue(
            metric=LLMAnswerRelevance(),
            gte=0.7,  # greater than or equal
            name="Answer Relevance >= 0.7",
        ),
        # 事实一致性不低于0.8
        TestMetricValue(
            metric=LLMFaithfulness(),
            gte=0.8,
            name="Faithfulness >= 0.8",
        ),
        # 有害内容占比不超过5%
        TestShareOfFailed(
            metric=LLMHarmfulness(),
            threshold=0.05,
            name="Harmful rate <= 5%",
        ),
    ],
    dataset=dataset,
)

suite.run()
suite.save("/tmp/llm_test_report.html")

# 在CI中：如果测试失败就exit(1)
if not suite.is_passed():
    print("❌ LLM Evaluation FAILED")
    for test in suite.tests:
        if not test.is_passed():
            print(f"  - {test.name}: {test.status.value} "
                  f"(expected {test.condition}, got {test.metric.value})")
    exit(1)
else:
    print("✅ All LLM tests passed")
```

## 踩坑记录

### 1. Judge LLM 的偏差不可忽视

用GPT-4当评判模型去评判GPT-4的产出——存在 **self-enhancement bias**。GPT-4倾向于给自己的回答打高分。实测数据：

| Judge Model | Target Model | Faithfulness Score (avg) | 偏差方向 |
|------------|-------------|------------------------|---------|
| GPT-4o     | GPT-4o      | 0.91                    | 偏高     |
| GPT-4o     | Claude-3.5  | 0.83                    | 基准     |
| Claude-3.5 | GPT-4o      | 0.79                    | 偏低     |
| Claude-3.5 | Claude-3.5  | 0.87                    | 偏高     |

**对策**：使用不同家族的评判模型（如用Claude评估GPT的产出），或采用多模型投票机制。

### 2. 评分稳定性问题

同一组数据跑两次，分数可能差5-10个百分点。这是LLM judge温度参数导致的。解决方案：

```python
# 降低评判模型的随机性
judge = LLMJudge(
    model="gpt-4o-mini",
    temperature=0.0,  # 务必设为0
    seed=42,          # 部分模型支持
    max_retries=3,
)
```

但temperature=0也不完全确定——OpenAI的API文档说了，即使temperature=0也有微小随机性。**建议对每组测试跑3次取中位数**。

### 3. Context 截断问题

RAG系统的context通常很长，可能超过LLM judge的上下文窗口。Evidently默认截断中间部分，但这样会丢失关键信息。

```python
# 自定义截断策略：保留头和尾
judge = LLMJudge(
    model="gpt-4o-mini",
    context_truncation="head_tail",  # 保留前30%和后30%
    max_context_tokens=8000,
)
# 或：分段评估，取最低分
```

## 性能开销与优化

LLM评估最蛋疼的地方是**慢且贵**。一次完整评估跑500个样本，用gpt-4o大概要5-10分钟、花费$2-5。

| 策略 | 耗时(100样本) | 成本 | 准确度 |
|------|-------------|------|--------|
| gpt-4o-mini | 2min | $0.05 | 中 |
| gpt-4o | 5min | $1.50 | 高 |
| 本地Qwen2.5-7B | 15min | $0 | 中低 |
| 抽样100条 | 快 | 低 | 取决于分布 |

**生产建议**：
- 每次PR全量跑用gpt-4o-mini + 抽样（关键场景用gpt-4o）
- 每日nightly跑全量用gpt-4o
- 本地开发用pytest + 少量cases快速验证

## 集成到CI/CD

```yaml
# .github/workflows/llm-eval.yml
name: LLM Evaluation
on: [pull_request]
jobs:
  evaluate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install -r requirements.txt
      - run: |
          python -m pytest tests/llm_eval.py \
            --evidently-report=/tmp/report.html \
            --evidently-json=/tmp/report.json
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      - uses: actions/upload-artifact@v4
        with:
          name: llm-eval-report
          path: /tmp/report.html
      - name: Check evaluation result
        run: |
          python -c "
          import json
          r = json.load(open('/tmp/report.json'))
          if not r['passed']:
              print('::error::LLM evaluation failed')
              exit(1)
          "
```

## 进阶方向

1. **自定义Metric**：框架允许用Python写自己的评估函数，比如检查JSON结构的key完整性、SQL查询的正确性、代码生成的可编译性
2. **数据集漂移监控**：Evidently 原生支持数据漂移检测——生产环境中用户query的分布变了，可以自动告警
3. **A/B Test 框架**：PairwiseMetric 可以对比两个模型/两版prompt在同一批输入上的表现差异，用统计检验判断优劣
4. **CI 门禁分级**：critical path用严格的threshold，非核心场景用宽松的threshold，不要一把尺量所有

LLM应用的质量保障还在早期，Evidently 代表了一个正确的工程化方向：把LLM评估变成代码、变成指标、变成自动化流水线的一环。下一步，评估框架本身的可信度（谁来判断judge对不对）是个更深的课题——但那是另一个话题了。
