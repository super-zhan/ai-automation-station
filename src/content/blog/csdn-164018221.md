# Prompt回归测试自动化：用 promptfoo 的断言矩阵把提示词质量钉死在 CI 里

提示词改动是 AI 应用里风险最高、又最没人管的变更：改一个词，线上回答风格可能整个漂移，而"感觉变好了"通常只是模型心情好。传统做法是人工点检几十条用例，或者写一堆 `if "关键词" in response` 的脆弱断言——前者回归成本高，后者把非确定性输出当字符串比，flake 到没法用。promptfoo（GitHub 24.5k+ stars）把这件事做成了正经工程：YAML 声明式配置 + 断言矩阵 + LLM-as-Judge，跑一次 `npx promptfoo eval` 就能对多模型、多 prompt 版本批量打分，接进 CI 当回归测试跑。本文拆它的断言体系、LLM-as-Judge 的落地方式和我在实际项目中踩过的坑。

## 核心机制：prompt、provider、assert 三段式

promptfoo 的整个模型就三个概念：**prompts**（要测的提示词，支持多版本对比）、**providers**（被测对象，OpenAI/Claude/本地模型/Agent 接口都行）、**asserts**（通过/失败的判定规则）。一条用例 = 固定的测试输入 + 一组断言。

```yaml
# promptfooconfig.yaml
prompts:
  - "你是客服，回答用户问题，必须引用知识库来源。\n问题: {{question}}"
  - "回答用户问题。\n问题: {{question}}"

providers:
  - openai:gpt-4o
  - anthropic:claude-sonnet-4

tests:
  - vars:
      question: "你们的退款政策是什么？"
    assert:
      - type: contains
        value: "30天"            # 确定性断言：必须出现关键条款
      - type: llm-rubric
        value: "回答必须引用知识库来源，未引用则失败"
      - type: javascript
        value: "output.length < 200"   # 自定义逻辑，超长回答判失败
```

跑 `npx promptfoo eval` 后，每个 (prompt × provider × test) 交叉点都会产出一行结果：pass/fail + 耗时 + 成本。一个矩阵测试下来，哪个 prompt 版本在哪个模型上退化，一眼可见。

## 断言的三个层级

| 断言类型 | 判定方式 | 适用场景 | 稳定性 |
|---|---|---|---|
| `contains` / `equals` / `regex` | 字符串匹配 | 关键词、格式、硬性约束 | 高，但脆弱 |
| `javascript` / `python` | 执行自定义代码 | 长度、JSON schema、调用自定义函数 | 高，灵活 |
| `llm-rubric` / `model-graded` | 另一个 LLM 按评分标准打分 | 忠实度、语气、风格、质量 | 中，需要校准 |

关键认知：**确定性断言负责"底线"，LLM-as-Judge 负责"质量"**。`contains` 保证"必须提到退款期限"，`llm-rubric` 判断"回答是否忠实于知识库"。两层缺一不可——只用 LLM 打分，成本高且判定波动；只用字符串断言，抓不住语义退化。

## LLM-as-Judge 的正确用法

Judge 不是"让 GPT 评个分"这么简单，我踩过三个坑：

**1. 评分标准必须可证伪。** 写"回答质量高"这种 rubric，Judge 就是在掷骰子。要写成可判定的行为描述：

```yaml
- type: llm-rubric
  value: |
    以下情况判 FAIL：
    - 回答中出现了知识库中不存在的事实
    - 用户问 A，回答的是 B
    - 引用了来源但没有对应内容
    其他情况判 PASS。
```

**2. 用少数派投票而不是单点判定。** 同一个输出让 Judge 跑 3 次取多数，或者用 3 个不同模型各判一次。单次 LLM 判定在边界样本上的一致性只有 80% 左右，3 次多数投票能压到 95% 以上。

**3. Judge 的模型要固定。** Judge 用 gpt-4o、被测对象用 claude，评估结果才有可比性。Judge 模型一换，历史分数线全部失效。

## 接进 CI：回归测试的正确姿势

promptfoo 有原生缓存（同样的 prompt+provider+test 组合第二次跑直接命中），配合 `--max-concurrency` 控制并发，一次全量 eval 可以压到分钟级，适合进 PR 检查：

```yaml
# .github/workflows/prompt-regression.yml
name: prompt-regression
on: [pull_request]
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npx promptfoo@latest eval --output /tmp/report.json
      - run: npx promptfoo@latest assert --config promptfooconfig.yaml
```

`eval` 生成报告，`assert` 按退出码判定——有失败用例就红，跟单测一样。注意：**CI 里一定要开缓存并固定 Judge 模型**，否则每次 PR 的分数线都在漂。

## 踩坑记录

- **缓存误伤**：改了 prompt 但文件名没变，promptfoo 按内容 hash 缓存，理论上不会误伤；但如果你在 prompt 里拼了动态时间戳之类的变量，记得把该变量排除出 hash 或关缓存，否则永远在测旧内容。
- **阈值校准**：上线第一周先跑"观察模式"（只记录不 fail），收集 200+ 真实样本的分数分布，再定 fail 线。拍脑袋定的阈值不是太松就是太紧。
- **变量污染**：测试用例的 vars 里带上下文长度、few-shot 示例，这些会直接影响分数。回归测试集要固定上下文，否则你测的是"上下文漂移"而不是"prompt 变更"。
- **成本控制**：矩阵是乘法——5 个 prompt × 4 个模型 × 50 条用例 = 1000 次调用。全量跑之前先用 `--filter` 圈一个小集快速验证配置正确，再放全量。Judge 调用也计入成本，用便宜的强模型（如 gpt-4o-mini 级别）做 Judge 通常够用。
- **测试集要"生长"**：线上收集到 Badcase 就往 tests 里加，promptfoo 支持从 CSV/JSON 导入测试集，每周从线上日志捞 10 条真实翻车样本补进去，回归测试才有生命力。光靠手写用例的测试集，测不出真实世界的分布。

## 进阶方向

- **Red Team 模式**：promptfoo 内置 redteam 命令，自动生成提示词注入、越狱、数据泄露等攻击用例，`npx promptfoo redteam generate` 就能开测，适合把安全测试也纳入同一套 CI。
- **Agent 测试**：promptfoo 支持把 Agent 作为 provider，断言工具调用序列、中间步骤，可以把本文的套路平移到 Agent 回归上。
- **和可观测性打通**：eval 报告和线上 tracing（Langfuse、Opik 这类）对不上是常见痛点——离线评估集 + 线上真实流量双轨，线上样本定期回流到测试集，形成闭环。

提示词质量不该靠"感觉"和"运气"。用断言矩阵兜底、用 LLM-as-Judge 抓语义退化、用 CI 锁回归，一套配置下来，prompt 改动从"玄学"变成"可回滚的工程变更"。
