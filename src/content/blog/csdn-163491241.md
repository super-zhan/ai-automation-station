# Agent记忆架构：拒绝扁平向量堆，L0-L3分层+符号画布把长任务token砍掉61%

GitHub trending 今天挂着一个 13.5k star 的仓库 TencentDB-Agent-Memory，解决的问题非常具体：Agent 跑长任务时，上下文被工具日志撑爆，而传统记忆系统把对话碎片化后平铺进向量库，召回退化成盲搜。它的答案是两个词：**分层（Layering）**和**符号化（Symbolization）**——短期记忆用 Mermaid 符号画布压缩工具日志，长期记忆把碎片对话蒸馏成 L0 对话 → L1 原子事实 → L2 场景 → L3 人设的四层语义金字塔。官方基准数据：接入 OpenClaw 后 WideSearch 任务成功率 +51.52%（相对）、token 消耗 −61.38%，PersonaMem 人设记忆准确率从 48% 提到 76%。这套架构对做 RAG 评测和 Agent 测试的人尤其有参考价值——它把"记忆质量"从玄学变成了可下钻验证的链路。

## 为什么扁平向量库是错的

多数记忆方案是"把对话切碎 → 全塞进 vector store → 相似度召回"。两个致命问题：

1. **召回没有宏观引导**。碎片之间没有层级关系，"用户今天偏好简洁回复"这种跨会话结论，靠 embedding 相似度永远召不回——它存在于 50 轮对话的统计规律里，不在任何单条文本里。
2. **上下文爆炸**。长任务的工具输出（搜索结果、代码、报错栈）动辄几十万 token，全量塞上下文，模型注意力被稀释，成本线性上涨。

TencentDB-Agent-Memory 的核心主张：记忆的**形成**和**召回**都必须是分层的，且压缩必须**可逆**——上层抽象永远保有一条通向下层原始证据的确定性路径。

## 短期记忆：三层结构 + Mermaid 符号画布

短期记忆（任务内）分三层，从上到下信息密度递减、证据完整性递增：

| 层 | 存储 | 内容 |
|---|---|---|
| 顶层 | Mermaid canvas | 任务状态转移图，带 `node_id`，仅几百 token 注入上下文 |
| 中层 | JSONL | 每步的 step-level 摘要 |
| 底层 | `refs/*.md` | 完整工具日志原文 |

工作流是"上下文卸载（context offload）"：工具日志全文落盘到外部文件，上下文里只留一张轻量 Mermaid 状态图；Agent 在图上推理，需要核实细节时按 `node_id` 精准取回原文。原理示意：

```mermaid
graph LR
    Log["完整工具日志（数十万 token）"] -->|1. 全文卸载| FS[("外部文件系统 refs/*.md")]
    Log -->|2. 抽取关系| MMD["Mermaid 画布（含 node_id）"]
    MMD -->|3. 轻量注入| Agent["Agent 上下文（几百 token）"]
    Agent -. 4. 按 node_id 取回 .-> FS
```

为什么选 Mermaid 而不是 JSON 或自然语言摘要？README 里写得很直白：Mermaid 语法密度高，LLM 能精确解析状态转移，人类也能直接读。实测就是 WideSearch 任务 token 从 221.31M 降到 85.64M（−61.38%），成功率反而从 33% 涨到 50%——上下文瘦身后模型注意力不再被垃圾日志稀释。

## 长期记忆：L0→L3 语义金字塔

跨会话记忆不做扁平日志，而是逐层蒸馏：

```
L3 Persona（人设：偏好、语气、长期目标）      ← persona.md，可读
L2 Scenario（场景块：一类任务的标准解法）
L1 Atom（原子事实：日期、项目细节、具体约定）
L0 Conversation（原始对话，证据底层）
```

触发机制是异步流水线：每 N 轮对话（默认 5）跑一次 L1 抽取，每新增 50 条记忆生成/更新一次 L3 人设；空闲 600 秒也会触发 L1。关键点：**上层只承载判断和方向，下层承载证据和精度**。用户问"我上次说的部署流程是什么"，先看 L3/L2，需要精确细节再下钻 L1/L0。

存储是异构的：底层事实和日志进数据库（默认 SQLite + sqlite-vec，可换腾讯云向量库 TCVDB）做全文检索；上层人设、场景、画布存成 Markdown 文件——"底层保证据，上层保结构"。所有中间产物都落在 `~/.openclaw/memory-tdai/`，可以直接打开看。

## 召回：BM25 + 向量 + RRF 融合

召回默认 `hybrid` 策略，不是单一 embedding：

```jsonc
{
  "memory-tencentdb": {
    "config": {
      "recall": {
        "strategy": "hybrid",        // keyword / embedding / hybrid(RRF融合)
        "maxResults": 5,
        "maxCharsPerMemory": 0,      // 单条记忆注入字符上限，0=不限
        "maxTotalRecallChars": 0,    // 总注入预算
        "timeoutMs": 5000            // 超时直接跳过注入，不阻塞对话
      },
      "bm25": { "language": "zh" }   // 中文用 jieba 分词
    }
  }
}
```

两个工程细节值得抄：

- **recall.timeoutMs=5000 且超时静默跳过**。记忆系统是旁路，绝不允许拖慢主对话——这是 Agent 插件设计里最容易被忽略的稳定性原则。
- **BM25 中文分词用 jieba**。纯向量召回对中文人名、专有名词、精确 ID 的匹配是弱项，关键词召回补位，最后 RRF（Reciprocal Rank Fusion）合并排序。

## 踩坑记录：embedding 的 Matryoshka 陷阱

接自建 embedding 服务时有个高频坑：OpenAI `text-embedding-3-*` 依赖请求体里的 `dimensions` 字段做 Matryoshka 截断，但 BGE-M3 这类开源模型不支持自定义维度，会直接回 HTTP 400 `does not support matryoshka representation`。解法是显式关掉：

```json
{
  "embedding": {
    "provider": "openai",
    "baseUrl": "http://your-host:your-port/v1",
    "model": "bge-m3",
    "dimensions": 1024,
    "sendDimensions": false
  }
}
```

## 测试开发视角：这套记忆怎么测

这才是这个项目对测试最值钱的部分——它把记忆质量评测做成了可复现的基准：

- **连续长会话评测，不是单轮抽测**。SWE-bench 一个 session 连续跑 50 个任务，模拟真实长任务的上下文累积压力；WideSearch 也是长 horizon 会话。单轮评测测不出记忆系统，因为记忆的价值恰恰在上下文累积后。
- **四个基准各测一个维度**：WideSearch（短期记忆对工具日志的压缩与恢复）、SWE-bench（压缩后任务成功率不降）、AA-LCR（长上下文推理）、PersonaMem（人设记忆准确率 48%→76%）。
- **白盒可调试**。召回错了不再是"看一堆向量分数"，而是沿 Persona → Scenario → Atom → Conversation 链路走一遍，根因必然落在这条链的某一环。L2 场景块、L3 人设都是纯 Markdown，打开就能检查。

| 基准 | 测什么 | 无插件 | 有插件 | 相对变化 |
|---|---|---|---|---|
| WideSearch | 短期记忆/压缩恢复 | 33% | 50% | +51.52% |
| SWE-bench | 压缩后任务成功率 | 58.4% | 64.2% | +9.93% |
| AA-LCR | 长上下文推理 | 44.0% | 47.5% | +7.95% |
| PersonaMem | 人设记忆准确率 | 48% | 76% | +59% |

token 侧：WideSearch 221.31M→85.64M（−61.38%），SWE-bench 3474.1M→2375.4M（−33.09%）。

做 Agent 评测的朋友可以直接抄这套方法论：**评测集要按记忆能力维度切分，session 要长，指标要同时报成功率与 token 成本**——只报成功率不报成本，压缩类方案永远吃亏；只报成本不报成功率，压缩质量无从验证。

## 落地建议

1. **先零配置跑**。OpenClaw 装插件后 `{"memory-tencentdb": {"enabled": true}}` 即生效，默认 SQLite 后端，不需要任何调参。
2. **调参从 Level 1 开始**。90% 场景只需要动 `recall.maxResults`、`pipeline.everyNConversations`（默认 5 轮抽一次 L1）、`persona.triggerEveryN`（默认 50 条新记忆生成一次人设）。
3. **长任务再开 offload**（需 ≥0.3.4）。`offload.enabled: true` 后注册 `contextEngine` slot，跑一次 patch 脚本钩住 `after-tool-call` 消息。触发阈值可调：`mildOffloadRatio`（上下文窗口 50% 温和压缩）、`aggressiveCompressRatio`（85% 激进压缩）、`mmdMaxTokenRatio`（画布注入 token 预算 20%）。
4. **Gateway 暴露到非 loopback 时必须开鉴权**。`TDAI_GATEWAY_API_KEY` 一设，除 `/health` 外所有路由都要 Bearer token，且比较是常数时间的；`TDAI_CORS_ORIGINS` 默认空列表（不发 CORS 头，浏览器全拦），生产别图省事设 `["*"]`。

## 进阶方向

项目 roadmap 里三个未完成项正好是记忆系统的下一个战场：跨 Agent/跨框架/跨设备的**便携记忆**（导入导出与热迁移）、**自动 Skill 生成**（从执行轨迹蒸馏可复用 SOP）、**可视化调试与记忆可观测性仪表盘**。其中"记忆可观测性"对测试最有想象空间——把 Persona→Scenario→Atom 的下钻链做成 UI，记忆评测就能从"跑分"进化成"根因定位"。

一句话总结：记忆系统的正确姿势不是"记得更多"，而是"该记的记、该扔的扔、要查能查"。分层保证召回有宏观引导，符号化压低上下文成本，可逆下钻链保证压缩不丢证据——三个设计互相咬合，缺一个都会退化回扁平向量堆。
