# Promptfoo：23K Stars 的 LLM 测试框架，从 Prompt 评估到红队测试实战

## 为什么需要专门的 LLM 测试框架

LLM 应用的输出是非确定性的。同一个 prompt、同一个模型，两次调用可能给出不同的回答。传统软件测试的断言思维（输入 X → 期望输出 Y）在 LLM 场景下基本失效。更棘手的是，Prompt 的微小修改可能引发模型行为剧变——加一个空格、换一个同义词，输出质量可能天差地别。

Promptfoo 解决的核心问题很直接：**用声明式配置驱动 LLM 评估，把 prompt 测试纳入 CI/CD 流程**。它不要求你写复杂的测试代码，而是通过 YAML 配置文件定义 prompt 模板、模型 provider、测试用例和断言规则，然后批量执行评估并生成可视化的对比报告。

这个项目目前 23K+ Stars，已被 OpenAI 收购但仍保持 MIT 开源。它支撑了超过 1000 万用户的 LLM 生产应用，被 Anthropic 和 OpenAI 内部使用。核心价值在于把「凭感觉调 prompt」变成了「数据驱动的评估循环」。

## 架构设计：声明式配置 + Provider 抽象 + 断言引擎

Promptfoo 的核心架构分为三层：

```
┌─────────────────────────────────────┐
│            CLI / API Layer           │
│   promptfoo eval / promptfoo view   │
├─────────────────────────────────────┤
│         Evaluation Engine            │
│  ┌─────────┐  ┌──────────┐  ┌────┐  │
│  │Provider │  │ Assertion│  │Var │  │
│  │ Router  │  │ Engine   │  │Sub │  │
│  └─────────┘  └──────────┘  └────┘  │
├─────────────────────────────────────┤
│         Provider Adapters           │
│ OpenAI  Anthropic  Ollama  vLLM... │
├─────────────────────────────────────┤
│        Output / Reporting           │
│   Local Web UI    CLI Table   JSON  │
└─────────────────────────────────────┘
```

最值得关注的是 **Provider 抽象层**。它定义了统一接口，让同一个 prompt 可以同时在 GPT-5.5、Claude Sonnet 4、DeepSeek V4 上运行并横向对比。Adapter 模式使得添加新 provider 只需要实现 `callApi()` 和 `callEmbeddingApi()` 两个方法。

**断言引擎** 是另一个关键设计。它不是简单的字符串匹配，而是支持语义类断言，包括：

| 断言类型 | 作用 | 示例 |
|---|---|---|
| `contains` / `icontains` | 字符串包含（大小写敏感/不敏感） | 检查输出包含特定关键词 |
| `equals` / `iequals` | 精确匹配 | 严格输出验证 |
| `starts-with` / `ends-with` | 前缀/后缀匹配 | URL 格式校验 |
| `is-json` | JSON 格式验证 | 结构化输出检查 |
| `contains-any` | 任意匹配 | 多个可能的正确输出 |
| `llm-rubric` | LLM 作为评判者 | "回答是否包含技术细节" |
| `model-graded-closedqa` | 模型闭卷评分 | 基于参考答案的评分 |
| `cost` | Token 花费上限 | 预算控制 |
| `latency` | 响应时间 P99 | 性能约束 |
| `perplexity` / `perplexity-score` | 困惑度评估 | 输出质量量化 |

`llm-rubric` 是最实用的断言类型之一——你告诉 LLM 评判标准，它自己判断输出是否符合要求。这绕过了传统断言无法处理语义模糊性的问题。

## 实战：搭建 Prompt 评估流水线

### 安装与初始化

```bash
npm install -g promptfoo
# 或 brew install promptfoo
# 或 pip install promptfoo

mkdir my-llm-eval && cd my-llm-eval
promptfoo init --example getting-started
```

初始化后会生成一个 `promptfooconfig.yaml`，这是整个评估的核心配置文件。

### 配置深度解析

以下是一个生产级的配置示例，覆盖多模型对比 + 多维度断言：

```yaml
description: '客服摘要生成模型评估'

prompts:
  - '请将以下客服对话摘要为3-5个要点，使用中文：{{dialog}}'
  - '请将以下客服对话整理为结构化摘要，包含：问题类型、处理结果、客户情绪：{{dialog}}'

providers:
  - openai:chat:gpt-5.5
  - anthropic:messages:claude-sonnet-4-6
  - openai:chat:gpt-5.4-mini
  # 本地模型
  - id: ollama:chat:qwen2.5:32b
    config:
      apiBase: http://localhost:11434

tests:
  - description: '退货退款场景 - 基础要求检查'
    vars:
      dialog: |
        客户：你好，我上周买的东西想退货。
        客服：请问是什么原因呢？
        客户：尺寸不合适，我买大了。
        客服：好的，商品在七天退换期内。请问您需要上门取件还是自己寄回？
        客户：上门取件吧。
        客服：好的，已经为您预约了明天下午的取件。退款会在我们收到商品后三个工作日内原路返回。
    assert:
      - type: contains
        value: '退货'
      - type: llm-rubric
        value: '摘要必须包含退货原因（尺寸不合适）和处理方式（上门取件）'
      - type: latency
        value: 8000
        provider: openai:chat:gpt-5.4-mini

  - description: '投诉场景 - 情绪识别检查'
    vars:
      dialog: |
        客户：你们什么破物流！说好三天到，现在五天了还没到？
        客服：非常抱歉给您带来不便，我帮您查一下单号……
        客户：别跟我查，我不在乎什么时候到，我要投诉！
        客服：理解您的心情，我马上为您转接投诉部门主管。
    assert:
      - type: llm-rubric
        value: '摘要应识别客户情绪为"愤怒"，并注明已转接投诉部门'
      - type: contains-any
        value:
          - '愤怒'
          - '不满'
          - '投诉'
```

关键配置项说明：

1. **prompts** 数组：多个 prompt 模板，系统会对所有 prompts × all providers × all tests 做笛卡尔积执行
2. **providers**：支持带独立配置的 provider 声明（如本地模型的 apiBase）
3. **tests[].assert**：每个测试用例可以有多个断言，全部通过才算 PASS
4. **latency 断言**：可以指定具体 provider，只对该 provider 生效

```bash
promptfoo eval
```

输出示例：

### 缓存机制

Promptfoo 内置了 LLM 响应缓存，默认存储在 `~/.cache/promptfoo/`。相同输入不会重复调用 API，这对迭代调优非常关键：

```bash
# 强制清除缓存（修改 prompt 模板后自动失效）
promptfoo eval --no-cache
# 或指定缓存位置
promptfoo eval --cache-file /tmp/custom-cache.db
```

缓存 key 基于 (prompt_hash + provider + model + temperature + vars) 的组合哈希生成，保证了不同参数组合不会被误命中。

## RAG 评估：不仅仅是检索测试

RAG（检索增强生成）系统的评估比纯 LLM 调用复杂得多——你需要同时评估检索质量和生成质量。Promptfoo 通过 `rag` 类型测试用例处理这个场景。

```yaml
tests:
  - description: 'RAG 管道端到端评估'
    vars:
      query: '什么是微服务架构的断路器模式？'
      context: |
        断路器模式是微服务架构中的一种容错设计模式。
        当某个服务的故障率达到阈值时，断路器"跳闸"，后续请求直接返回降级响应而非继续调用故障服务。
        断路器有三种状态：关闭（正常调用）、打开（直接降级）和半开（尝试恢复）。
        常用实现框架：Resilience4j（Java）、Hystrix（Netflix，已维护模式）。
    assert:
      # 检索质量评估
      - type: llm-rubric
        value: '输出应该引用上下文中提供的具体信息'
      # 幻觉检测
      - type: llm-rubric
        value: '输出不能包含上下文中没有的信息'
      # 回答质量
      - type: llm-rubric
        value: '回答应该清晰解释断路器模式的三种状态及其转换条件'
      # 性能约束
      - type: latency
        value: 5000
```

这里的关键洞察是：**RAG 评估的核心不是测试检索器返回了什么，而是测试生成器是否忠实地使用了检索结果**。`llm-rubric` 在这里充当了「忠实度检测器」——如果 LLM 输出了上下文不存在的信息，就是幻觉。

## 红队测试（Red Teaming）：自动化安全扫描

2026 年 7 月的最新版本（v0.121.18）中，红队能力进一步增强。Promptfoo 提供了预置的攻击 payload 库，覆盖 OWASP LLM Top 10 分类：

```bash
promptfoo redteam init
promptfoo redteam run
```

配置示例：

```yaml
# redteam_config.yaml
redteam:
  plugins:
    - id: 'jailbreak'
    - id: 'prompt-injection'
    - id: 'excessive-agency'
    - id: 'harmful-content'
      config:
        categories:
          - 'hate-speech'
          - 'violence'
          - 'self-harm'
  numTests: 50
  target:
    id: openai:chat:gpt-5.5
    config:
      temperature: 0
```

输出报告包含每个攻击向量的成功率、payload 示例和模型具体响应。这在把 LLM 应用推向生产前是必须的一步——GPT-5.5 在未加固时对某些 jailbreak 变体的成功率可能高达 15-20%。

## CI/CD 集成与质量门禁

Promptfoo 最实用的功能之一是回归测试门禁。在 CI 中配置：

```yaml
# .github/workflows/llm-eval.yml
name: LLM Eval
on: [pull_request]
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm install -g promptfoo
      - run: promptfoo eval
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      - run: promptfoo check --threshold 0.8
```

`promptfoo check` 命令会根据配置的阈值判断本次评估是否通过。如果新 prompt 的通过率低于 80%，CI 会 fail，阻止合并。这防止了「不小心改坏 prompt」上线后才被发现。

## 踩坑记录

1. **llm-rubric 的评判偏差**：LLM 作为评判者存在位置偏见——倾向于认可与自己风格相似的输出。解决方案是多个 rubric 交叉验证，或使用不同的评判模型（如用 Claude 评估 GPT 的输出）。

2. **缓存污染**：修改 prompt 模板后，如果模板变量的默认值没变，缓存可能命中旧结果。建议在迭代开发时用 `--no-cache` 跑一次全量评估，确认结果后再启用缓存。

3. **Cost 控制**：多模型 × 多 prompt × 多测试用例的笛卡尔积可能导致大量 API 调用。一个中等规模评估（3 prompts × 4 providers × 50 tests）可能消耗数百美元 token。建议先用小样本（--max-concurrency 控制并发）跑通配置。

4. **非确定性测试**：LLM 输出天然随机，同一个测试可能时而通过时而失败。解决思路是多次运行取统计结果，而非单次 PASS/FAIL 判定。Promptfoo 支持 `--repeat N` 参数执行多次。

## 总结与进阶方向

Promptfoo 把 LLM 测试从手动对比带到了自动化评估的层面。核心价值三点：声明式配置降低编写测试门槛、Provider 抽象实现多模型对比、断言引擎覆盖语义级验证。对于正在构建 LLM 应用的团队，它是把 prompt 工程从「艺术」变成「工程」的关键工具。

**进阶探索方向**：
- 集成 Langfuse / LangSmith 等可观测性平台，做生产环境评估数据的回传分析
- 自定义 Provider Adapter，对接内部自部署模型
- 利用 `promptfoo eval --output path/to/results.json` 导出结构化评估数据，做自定义可视化
- 结合测试金字塔策略：单元级用 `contains` 断言、集成级用 `llm-rubric`、端到端用红队扫描
