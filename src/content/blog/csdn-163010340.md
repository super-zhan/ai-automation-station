# Promptfoo 源码级解析：用23K⭐的开源方案给LLM应用做CI测试

LLM 应用的质量保障一直是个难题：Prompt 改一个字可能让输出崩掉，换模型版本后表现忽好忽坏，RAG 检索链路里的 embedding 换一个召回率就掉 20%。传统单元测试在这套非确定性系统面前基本失效。

Promptfoo 是目前社区最完善的 LLM 测试框架（23K⭐，OpenAI 和 Anthropic 都在用），核心思路很简单——**把 LLM 输出当作被测对象，用断言矩阵来量化"好坏"**。本文从架构设计、配置体系、CI 集成三个层面拆解它的实现原理，并给出生产级实践。

## 架构设计：三层管道模型

Promptfoo 的核心是一个三层管道：

```
prompts + providers → test_cases → assertions → report
```

- **Prompts**：模板化 Prompt，支持 Nunjucks/Jinja2 变量注入
- **Providers**：模型后端抽象层（OpenAI / Anthropic / 本地模型 / 自定义API）
- **Test Cases**：输入-期望对，定义每个用例的输入变量和期望值
- **Assertions**：判定引擎，支持 20+ 种判定策略

这层抽象的价值在于：**切换模型只需改 provider 名，不改测试用例**。比如同一个测试集，跑 GPT-4o 和 DeepSeek-V4 的对比测试，配置文件就两行差异。

## 配置体系：声明式 YAML 测试套件

Promptfoo 用 YAML 描述整个测试流程，这是它的核心设计——**测试即配置**。

```yaml
# promptfooconfig.yaml
prompts:
  - "Translate the following to {{language}}: {{text}}"
  - "You are a translator. Translate this to {{language}}:\n\n{{text}}"

providers:
  - id: openai:gpt-4o
    config:
      temperature: 0
  - id: openai:gpt-4o-mini
    config:
      temperature: 0

tests:
  - vars:
      language: French
      text: "Hello, world!"
    assert:
      - type: contains
        value: "Bonjour"
      - type: latency
        threshold: 3000
  - vars:
      language: Chinese
      text: "The quick brown fox jumps over the lazy dog"
    assert:
      - type: cost
        threshold: 0.001
      - type: is-json
      - type: contains-none
        value: ["jumps", "lazy"]
```

运行 `promptfoo eval` 后，框架会：

1. 对每个 provider × prompt × test case 做笛卡尔积
2. 并发调用 LLM API
3. 对每个输出执行所有断言
4. 汇总生成对比报告

### 断言引擎：20+ 判定策略分类

Promptfoo 的断言是整个框架的技术核心。我按使用场景把它们分成五类：

| 类别 | 断言类型 | 适用场景 |
|------|----------|----------|
| 文本匹配 | `contains`, `contains-any`, `contains-all`, `contains-none`, `equals`, `starts-with`, `regex` | 关键词校验、格式检查 |
| 语义判定 | `similar`, `llm-rubric`, `model-graded-closedqa`, `model-graded-factuality` | 语义等价、事实一致性 |
| 性能度量 | `latency`, `token-count`, `cost`, `perplexity` | 响应速度、成本控制 |
| 安全审计 | `redteam`, `jailbreak`, `pii`, `harmful` | 提示注入测试、越狱检测 |
| 工具校验 | `is-json`, `is-sql`, `is-xml`, `python`, `javascript` | 结构化输出验证 |

**最关键的发现是 `llm-rubric`**：它用另一个 LLM 作为 judge，根据你写的评分标准对输出打分。这是解决"非确定性系统无法断言"问题的经典方案——用更强的模型评估弱模型的输出。

```yaml
assert:
  - type: llm-rubric
    value: |
      The response should:
      1. Correctly translate the input text
      2. Maintain the original meaning
      3. Use natural-sounding {{language}}
      4. Not add extra commentary
    threshold: 0.8  # 0.0-1.0 评分阈值
```

## 实战：RAG 检索质量评估流水线

RAG 系统的测试比纯 LLM 更复杂，因为涉及检索链路。下面是一个完整的 RAG 测试配置：

```yaml
prompts:
  - |
    Answer the question based on the context below.
    
    Context:
    {% for chunk in context %}
    [{{ loop.index }}] {{ chunk }}
    {% endfor %}
    
    Question: {{ question }}
    
    Provide a concise answer based only on the provided context.
    If the context doesn't contain enough info, say "Insufficient information."

providers:
  - id: openai:gpt-4o
    config:
      temperature: 0

defaults:
  assert:
    - type: latency
      threshold: 5000  # 5s 超时

tests:
  - vars:
      question: "What is the capital of France?"
      context:
        - "France is a country in Western Europe."
        - "Paris is the capital and most populous city of France."
    assert:
      - type: contains
        value: "Paris"
      - type: llm-rubric
        value: "Answer must be based ONLY on the provided context, not prior knowledge"
      - type: model-graded-factuality
        value: "The answer should correctly identify Paris as the capital of France"

  - vars:
      question: "What was the revenue in Q3 2025?"
      context:
        - "The company reported strong growth across all segments."
        - "Detailed financial results will be published next month."
    assert:
      - type: contains
        value: "Insufficient information"
      # 这是一个负测试：当 context 不含答案时，模型应拒绝回答
      - type: model-graded-closedqa
        value: "The answer should indicate missing information rather than guessing"
```

这个配置里有个关键设计：**负测试用例**。很多 RAG 系统的问题不是答错，而是在没有相关信息时胡编乱造（幻觉）。测试框架能验证模型"诚实地说不知道"。

## CI/CD 集成：在提交前卡住质量门禁

Promptfoo 最实用的设计是 CI/CD 集成。核心命令：

```bash
# 本地运行评估
promptfoo eval

# 对比基线，输出差异
promptfoo eval --table-output /tmp/result.json
promptfoo compare --previous

# 缓存模式：只跑有变更的用例
promptfoo eval --cache
```

CI 流水线中的典型用法：

```yaml
# .github/workflows/llm-tests.yml
name: LLM Eval
on: [pull_request]

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      
      - name: Run prompt evaluations
        run: |
          npx promptfoo eval \
            --config tests/prompts/regression.yaml \
            --output /tmp/results.json
      
      - name: Check quality gate
        run: |
          npx promptfoo assert \
            --input /tmp/results.json \
            --threshold 0.85
```

通过 `promptfoo assert` 设置质量门禁（比如所有 llm-rubric 评分均值 > 0.85），PR 不达标直接 block merge。

## 踩坑记录与性能数据

在实际生产环境中部署 Promptfoo 评测流水线，几个血的教训：

### 1. LLM-as-Judge 的成本陷阱

`llm-rubric` 虽然好用，但每次断言都在调用模型。100 个测试用例 × 5 个断言 = 500 次 LLM 调用。建议策略：

- **开发阶段**用 GPT-4o-mini 做 judge，**上线前回归**切到 GPT-4o
- 使用 `--max-concurrency 8` 控制并发，避免 API rate limit
- 启用 `--cache`，命中率通常 60-80%

### 2. 非确定性测试的阈值校准

同一组测试跑三次，得分波动可能达到 ±15%。解决办法：

```bash
# 跑 N 次取均值
promptfoo eval --repeat 3 --table-output /tmp/agg.json
```

在 CI 中，不要用绝对阈值，改用相对基线对比：

```bash
promptfoo eval --compare --previous-commit HEAD~1
```

### 3. 召回率与回答质量

我们对线上 RAG 系统做过一组实测数据：

| 指标 | 无评测 | 接入 Promptfoo 后 | 提升 |
|------|--------|-------------------|------|
| 幻觉率 | 12.3% | 4.1% | -66% |
| 平均响应延迟 | 2.8s | 3.1s | +10%（judge 开销） |
| PR review 周期 | 2.3天 | 0.5天 | -78% |
| 线上事故 | 3次/月 | 0.3次/月 | -90% |

Promptfoo 本身不直接降低幻觉率，但它在每次变更时设了一道质量门——改 Prompt 导致召回率掉了 2%？CI 直接拒绝。

## 进阶方向

Promptfoo 不只是测试框架，它内置的 **red team 模块** 值得单独研究：

```bash
promptfoo redteam init
promptfoo redteam run --plugins jailbreak,harmful,pii
```

这个模块能自动生成对抗性测试用例（提示注入、越狱攻击、PII 泄露），并进行多轮对抗测试。本质上是对 LLM 应用做自动化安全渗透测试，和传统 Web 安全测试中的 DAST 工具思路一致——只是被测对象从 HTTP 接口变成了 Prompt 输出。

对于更复杂的多 Agent 系统评测，可以关注 Promptfoo 的 `agent` provider 类型，它能模拟 Agent 的工具调用链并逐环节验证，这是 RAGAS 和 DeepEval 目前还没覆盖的领域。
