# Coder Eval：用工程化方式给 AI 编程代理做自动化测试

写 Claude Code Skill 或者调教 Codex 的都踩过同一个坑：改了一版 prompt，觉得稳了，跑一下真实任务——行为完全变了，或者干脆 tool 都没触发。靠手工点验已经不够用了。

UiPath 最近开源的 [Coder Eval](https://github.com/UiPath/coder_eval) 解决了这个问题——它是一个专门给 AI 编程代理（Claude Code、Codex、Gemini）做评测的框架。核心思路很简单：**把评测任务写成声明式 YAML，在沙箱里跑真实代理，然后按加权标准打分。** 不是模型排行榜那种固定数据集，而是让你测自己的 task、自己的 skill、自己的 prompt。

## 架构设计：四个核心抽象

Coder Eval 的设计围绕四个层：

```
┌─────────────────────────────────────────────┐
│  Experiment Layer (A/B 配置比较)             │
├─────────────────────────────────────────────┤
│  Task Layer (YAML 声明式任务 + 评分标准)     │
├─────────────────────────────────────────────┤
│  Agent Abstraction (Claude/Codex/Gemini SPI) │
├─────────────────────────────────────────────┤
│  Sandbox Driver (tempdir / Docker)           │
└─────────────────────────────────────────────┘
```

**Task Layer** 是核心——一个 YAML 文件定义 prompt、agent 配置、沙箱环境和 success criteria。不像传统的 pass/fail 二元判定，它支持连续 0.0–1.0 加权打分，可以给部分分。

**Agent Abstraction** 通过 SPI（Service Provider Interface）统一了不同编程代理的调用方式。今天内置了 Claude Code、Codex、Google Antigravity/Gemini，想加新的自己实现接口就行。

**Experiment Layer** 是 A/B 测试的入口——同样的任务集，跑在不同 agent/model/prompt 配置下，结果直接对比。

**Sandbox Driver** 提供隔离执行环境。`tempdir` 驱动适合本地快速验证，`Docker` 驱动才是安全边界，跑不信任的任务必须用后者。

## 任务定义：YAML 声明的灵活评分体系

来看一个实际的 task 定义（来自仓库自带示例）：

```yaml
task_id: "hello_date_smoke_test"
description: "Create a Python script that prints 'Hello, Claude!' then the current date."
initial_prompt: "Create a Python file named app.py in the current working directory
  that prints 'Hello, Claude!' on one line, and today's date in YYYY-MM-DD format
  on the next line. Use the datetime module. Then run the script with: python app.py"
tags: [smoke, smoke-pass, golden, basic, pure-python]

run_limits:
  expected_turns: 5

agent:
  type: "claude-code"
  permission_mode: "acceptEdits"
  allowed_tools: ["Read", "Write", "Bash"]

success_criteria:
  - type: "file_exists"
    path: "app.py"
    description: "The file app.py must be created."
  - type: "file_contains"
    path: "app.py"
    includes: ["Hello, Claude!", "datetime"]
    description: "The script must contain the required string and import."
  - type: "run_command"
    command: "python app.py"
    timeout: 10
    description: "The script must execute successfully."
```

几个关键设计值得注意：

**criterion 类型丰富**：`file_exists`、`file_contains`、`run_command`、`code_similarity`、`llm_judge`（用 LLM 做裁判打分）。实际项目里最常用的是 `llm_judge`——给一个 rubric，让模型判输出质量。

**连续评分而非二元判定**：每个 criterion 可以配置 weight + threshold，最终总分是加权和。比如 `file_exists` 权重 0.3，`run_command` 权重 0.4，`llm_judge` 权重 0.3——而不是单纯的 pass/fail。

**默认继承机制**：`agent` 段可以省略，从 experiment 配置里继承。这样同一个 task 可以跑在不同 agent 配置下做对比。

## A/B 实验层：比较不同模型和配置

Experiment 文件定义了一个实验矩阵：

```yaml
# experiments/default.yaml
experiment_id: "model_comparison_v1"
description: "Compare Claude Code vs Codex on skill suite"

agents:
  - type: "claude-code"
    model: "claude-sonnet-4-20260514"
    label: "claude-sonnet"

  - type: "claude-code"
    model: "claude-opus-4-20250514"
    label: "claude-opus"

  - type: "codex"
    model: "gpt-4.1"
    label: "codex-gpt4"

tasks: ["tasks/skill_suite/*.yaml"]
repetitions: 3  # 每个配置跑3次消除随机性
```

跑完后用 `coder-eval report` 看对比：

```bash
coder-eval run experiments/model_comparison_v1.yaml
coder-eval report runs/latest --compare
```

输出会按 label 分组展示每个 agent 的：总分、各 criterion 得分、token 消耗、成本、耗时。这个对比能力在选型时非常有用——同一个 task，Claude Opus 多花了 3 倍 token 但得分只高了 2%，那你可能选 Sonnet 就行。

## 实测：跑一个完整的评测流程

```bash
# 安装
uv tool install coder-eval

# 验证 task 定义（不消耗 token，纯校验 YAML 语法和 schema）
coder-eval plan tasks/hello_date.yaml

# 跑评测（会真实调用 Claude Code）
coder-eval run tasks/hello_date.yaml

# 查看报告
coder-eval report runs/latest
```

初次运行输出大概长这样：


## 踩坑记录

**1. Sandbox 不等于安全边界**

`tempdir` 驱动只是在临时目录跑，没有隔离。Coder Eval 的文档明确说了这不是安全边界。跑不信任的 task（比如社区贡献的评测集）必须用 `docker` 驱动。

**2. expected_turns 的微妙作用**

`run_limits.expected_turns` 是个软限制——超了不会 fail，但报告里会标记 banner 警告。实际价值在于：如果你的 skill 引导了 agent 行为，ideal turn 数应该是稳定的。突然暴涨说明 skill 可能没被触发，agent 在瞎绕。

**3. 非确定性是最大的敌人**

同样的 task、同样的 agent、同样的模型，两次跑可能分数不一样。Coder Eval 用 `repetitions` 参数来解决——建议至少跑 3 次取中位数，而非单次结果。Experiment 层的设计天然支持这个。

**4. Token 消耗不可忽视**

跑一个复杂任务集（10 个 task × 3 次重复 × 2 个 agent 配置）轻松消耗几十万 token，成本几十美元。在 CI 里每天跑不现实——建议 CI 只跑 smoke 集（2-3 个快速 task），完整评测走定时任务（nightly/weekly）。

## CI 集成：用 GitHub Actions 做回归门禁

```yaml
# .github/workflows/coder-eval-nightly.yml
name: Coder Eval Nightly
on:
  schedule:
    - cron: '0 6 * * 1-5'  # 工作日早上跑
  workflow_dispatch:       # 支持手动触发

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - name: Run evaluation suite
        run: |
          uv tool install coder-eval
          coder-eval run tasks/smoke_suite.yaml
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      - name: Gate on regressions
        run: |
          REPORT=$(coder-eval report runs/latest --json)
          SCORE=$(echo "$REPORT" | python3 -c "import sys,json; print(json.load(sys.stdin)['summary']['weighted_score'])")
          if (( $(echo "$SCORE < 0.8" | bc -l) )); then
            echo "❌ Score $SCORE below threshold 0.8"
            exit 1
          fi
          echo "✅ Score $SCORE passes"
```

这个 pipeline 每天晚上自动验证一遍 skill 是否还正常工作。如果模型升级或者 prompt 漂移导致某条 criterion 挂了，第二天早上就知道了，不用等用户报 bug。

## Coder Eval 与其他方案的定位差异

| 维度 | Coder Eval | SWE-bench | 手写脚本 |
|------|-----------|-----------|---------|
| 评测对象 | 你的 task/skill | 固定数据集 | 你的 task |
| 评分方式 | 加权连续 0–1 | pass/fail | 自己写 |
| A/B 实验 | 内置 | 无 | 自己搭 |
| 沙箱隔离 | tempdir/Docker | Docker | 可选的 |
| CI 集成 | CLI 原生支持 | 需要包装 | 自己写 |
| token/成本追踪 | 内置 | 无 | 自己加 |

Coder Eval 填补的恰好是"手写脚本太简陋，SWE-bench 又太死板"中间的那个位置。

## 总结与进阶方向

Coder Eval 的价值不在于又一个 benchmark，而在于**把 AI 编程代理的评测工程化了**。YAML 声明式任务、加权评分、A/B 实验、CI 门禁——这套工具链让评测从"手工点一点"变成了可复现、可对比、可自动化的工程流程。

进阶方向：
- 接入 PromptFoo 或 DeepEval 做 prompt 级别的评测对比
- 用 langfuse 或 wandb 追踪长期评测趋势
- 自建 task 数据集，覆盖你产品的核心场景
- 结合 diff 分析（比如 `code_similarity` criterion）做回归测试

如果已经在写 Claude Code Skill 或者调 Codex prompt，给它们上个自动化评测——效果比想象中大。
