# E2E 定位器自愈：启发式优先、AI 裁决、置信度兜底的三层架构

UI 自动化里 80% 的"失败"根本不是产品缺陷，而是定位器漂移：前端把 `.btn-primary` 改成 `.button--cta`，按钮文案从 "Sign in" 改成 "Log in"，或者组件外包了一层 div，测试就红了，测试同学花半小时定位、改 selector、重跑。这个循环消耗的工时比写测试还多。自愈（self-healing）解决的就是这件事：定位器匹配失败时，不直接判失败，而是用替代策略找到"同一个逻辑元素"，找不到或置信度不足时才真正失败。

关键认知：自愈不等于"测试永不失败"。它要区分两类失败——产品真 bug（必须大声失败）和定位器漂移（自动修复并留痕）。实现上推荐三层架构：**启发式规则兜底优先，AI 模型做决策，置信度阈值做最后闸门**。启发式便宜、确定、可解释，能覆盖七成场景；AI 只处理启发式搞不定的模糊匹配；置信度不足时宁可失败也不盲修——这是防止"假绿"的底线。

## 定位器为什么会坏

先列清楚故障模式，自愈策略才有针对性：

| 原因 | 示例 | 影响范围 |
|---|---|---|
| CSS 重构 | `.btn-primary` → `.button--cta` | 所有基于 class 的定位器 |
| DOM 结构调整 | 外层包了 div，`nth-child` 错位 | 位置选择器、XPath |
| 文案/复制变更 | "Sign in" → "Log in" | `getByText`、基于 name 的定位器 |
| 动态 ID | `#input-3f9a2` 每次构建重新生成 | 所有硬编码 ID |
| 国际化 | UI 渲染成其他语言 | 全量文本类定位器 |
| 异步渲染 | 元素在数据加载后才出现 | 不是真坏，但没 auto-wait 就像坏了 |

根因只有一个：测试耦合了本不该稳定的实现细节。class、生成的 ID、DOM 位置，前端重构时随便改。防御手段是"像用户一样定位元素"——按 role 和可访问名称找，而不是按 class 找。

## 第一步：让大多数定位器根本不用修

最便宜的自愈是"不需要自愈"。Playwright 的定位器优先级：role > label > testid > text，CSS/XPath 是最后手段：

```typescript
import { test, expect } from '@playwright/test';

test('resilient locators survive styling changes', async ({ page }) => {
  await page.goto('/login');
  // role + accessible name：class 和 DOM 怎么改都不受影响
  await page.getByRole('textbox', { name: 'Email' }).fill('user@example.com');
  await page.getByLabel('Password').fill('secret');
  // 没有语义角色的元素，用稳定的 test id
  await page.getByTestId('login-submit').click();
  await expect(page).toHaveURL('/dashboard');
});
```

配合统一的 test-id 约定，和前端约定好"没有语义角色的元素必须带 `data-testid`"：

```typescript
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  use: {
    testIdAttribute: 'data-testid',
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
  },
});
```

只做这一步，最大的一类定位器故障（CSS 重构）就消失了。自愈是兜底，不是偷懒的借口。

## 核心：自愈引擎的五段式架构

生产可用的自愈层通常由五部分组成：

```
测试代码 → 失败捕获 → 候选生成(启发式/历史/AI) → 置信度策略 → 审计上报
              ↑                                                    │
              └────────── 应用修复后继续执行 ←──────────────────────┘
```

1. **基线测试**：正常测试代码，用上文推荐的定位策略
2. **失败捕获**：记录失败的 selector、错误信息、测试文件、行号、URL、以及**截断后的 DOM 快照**（不是整个 document，快照太大会拖垮延迟和 token 成本）
3. **修复引擎**：生成候选定位器——按顺序尝试文本匹配、role+name 匹配、属性匹配、XPath 重算，每路候选带一个置信度分数；启发式算不出来的再交给 LLM
4. **置信度策略**：可配置阈值。分数达标才自动应用；不达标就原样抛错，把候选挂到报告里等人 review
5. **审计层**：每次自愈落一条 JSON 记录（旧定位器、新定位器、分数、策略、结果），进 dashboard。定位器漂移必须可观测，否则 selector 在静默变化，你会失去对套件的信任

引擎的配置项大概是这样的：

```typescript
const healingEngine = createHealingEngine({
  apiKey: process.env.HEALING_MODEL_API_KEY,
  healingStrategies: ['text', 'role', 'xpath', 'css'], // 启发式顺序
  confidenceThreshold: 0.8,   // 低于此值不自动应用
  maxRetries: 3,
  reportPath: './healing-reports',
});
```

测试侧只加一层薄包装，可读性不破坏：

```typescript
const primary = 'button:has-text("Submit")';
try {
  await page.click(primary);
} catch (error) {
  const result = await healingEngine.heal({
    originalLocator: primary,
    testFile: 'contact.spec.ts',
    lineNumber: 8,
    domSnapshot: await page.content(), // 生产环境建议截断/脱敏
    page,
    error,
  });
  if (result.success && result.confidence >= 0.8) {
    await page.click(result.newLocator);
  } else {
    throw error; // 置信度不够，宁可失败
  }
}
```

## 自定义 LLM fallback：从可访问性树里找元素

启发式覆盖不了的场景（比如文案大改、元素语义变了），才轮到 LLM。实现思路：主定位器失败时，抓取页面的 accessibility snapshot，展平成 role+name 候选列表，让模型从中选出最匹配意图的一个，返回 JSON，再用 `getByRole` 重试：

```typescript
import { type Page, type Locator } from '@playwright/test';

interface HealOptions { intent: string; page: Page; }

async function healLocator(opts: HealOptions): Promise<Locator | null> {
  const snapshot = await opts.page.accessibility.snapshot();
  const candidates = flattenSnapshot(snapshot);
  const chosen = await askModelForBestMatch({
    intent: opts.intent,          // "the primary sign-in button"
    candidates,                   // [{role:'button', name:'Log in'}, ...]
  });
  if (!chosen) return null;
  // 模型返回的 role+name 必须 grounded 在快照里，防止幻觉
  return opts.page.getByRole(chosen.role as any, { name: chosen.name });
}

function flattenSnapshot(node: any, acc: any[] = []): any[] {
  if (!node) return acc;
  if (node.role && node.name) acc.push({ role: node.role, name: node.name });
  for (const child of node.children ?? []) flattenSnapshot(child, acc);
  return acc;
}
```

两个工程要点：**候选必须来自真实快照**，让模型做选择题而不是填空题，从根上防幻觉；**返回结构用 JSON mode 强约束**，解析失败就返回 null 走失败路径，绝不猜测。

## 踩坑记录与实测数据

几个真实项目里踩过的坑：

- **LLM 幻觉候选**：直接让模型"写一个 selector"必翻车。改成"从候选列表里选一个"之后，误修率明显下降。模型只做排序，不做生成。
- **快照过大**：整页 HTML 喂给模型，单次 heal 延迟能到 10s+，token 成本也扛不住。只传 accessibility 树或截断后的 DOM，延迟能压到 1-3 秒。
- **重复 heal**：同一个元素每次跑都修一遍，等于每次都付一次 LLM 调用。把修复结果缓存起来（元素 key → 新定位器），后续运行直接命中缓存，开销归零。
- **自动提交修复**：heal 成功就直接改测试文件并提交，这是最危险的做法。修复必须进审计流，人工 review 后合并。Playwright 官方 healer agent 也是这个设计：它对比 trace（上次通过时元素的样子）和当前 DOM 快照给出 patch 建议，但**由人决定是否合入**——它是 repair assistant，不是 auto-committer。
- **低置信度静默通过**：阈值设太低，selector 修错了但断言恰好过了，制造假绿。阈值宁高勿低，0.8 起步；拿不准就失败——失败是安全的，假绿不是。

参考社区方案的实测口径：引入 role/testid 优先策略 + 自愈层后，定位器维护类 PR 减少约 60-80%；heal 一次平均 1-3 秒（缓存命中后为 0）；AI 参与决策的场景控制在总 heal 次数的 20-30%，其余由启发式规则直接命中。

## 收尾

自愈的本质是把"定位器维护"从线上事故变成离线审计。三层架构——启发式优先、AI 裁决、置信度兜底——每一层都在降低上一层的风险和成本：启发式把 AI 调用量压到最低，AI 补上启发式的召回率，置信度阈值保证任何一层出错都不会静默污染测试结果。加上缓存和审计流，自愈层就从"魔法黑盒"变成了可解释、可回滚、可度量的工程组件。

进阶方向：接入 Playwright 的 healer/planner/generator 测试代理族（配合 MCP server 在 Claude Code 工作流里直接出修复 patch）；把历史运行数据喂给候选生成器（上次这个逻辑步骤用什么定位器成功过，优先试它）；结合截图做视觉分析（DOM 分析失效时比对像素差异）；最后把自愈事件和 flaky test 分类器打通——哪些修复是合理的 UI 演进，哪些是产品 bug 的伪装，让数据自己说话。
