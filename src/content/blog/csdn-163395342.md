# Agent Skills + Playwright：让 AI 自己写 E2E 测试并执行的架构拆解

最近 GitHub 上有个项目值得测试开发同学关注：`lackeyjb/playwright-skill`（约 3k star），一个把 Playwright 浏览器自动化封装成 Claude Code Skill 的开源插件。核心思路一句话：**不再由人写死测试脚本，而是让 Agent 根据自然语言任务，自主编写 Playwright 代码、执行、断言、返回截图**。这篇文章从源码层面拆解它怎么做到"零模块解析错误"、"渐进式披露"、"无竞态清理"，以及这套模式与传统 E2E 测试、MCP Browser 工具的本质区别。

## 一、为什么是"Skill"而不是"MCP Tool"

先厘清概念。Agent Skills（规范见 agentskills.io，Anthropic 2025 年 10 月发布）是一个**文件夹**：`SKILL.md`（指令）+ 脚本 + 资源。Agent 通过 SKILL.md 里的 `description` 字段自主发现它，按需加载。

和 MCP Tool 的区别很关键：

| 维度 | MCP Tool | Agent Skill |
|---|---|---|
| 交互形态 | Agent 调用预定义的函数接口 | Agent 读取指令后**自己写代码**执行 |
| 灵活性 | 受限于工具暴露的参数 | 任意任务，不受预置脚本限制 |
| 上下文成本 | 工具定义常驻上下文 | 渐进式披露，按需加载 |
| 典型场景 | 固定的原子操作（搜索、发请求） | 复杂多步流程（完整测试会话） |

MCP 适合"可枚举的操作"，Skill 适合"无法穷举的任务"——写 E2E 测试正是后者：页面千变万化，预置脚本永远覆盖不全。playwright-skill 的定位就是"通用浏览器自动化"，Claude 每次针对具体任务现场写代码。

## 二、SKILL.md：发现机制与渐进式披露

Skill 的目录结构（插件格式）：

```
playwright-skill/
├── .claude-plugin/
│   ├── plugin.json          # 插件元数据
│   └── marketplace.json
└── skills/
    └── playwright-skill/
        ├── SKILL.md         # Agent 唯一必读的文件
        ├── run.js           # 通用执行器
        ├── API_REFERENCE.md # 完整 Playwright 参考，按需加载
        ├── package.json
        └── lib/helpers.js   # 可选工具函数
```

SKILL.md 的 YAML frontmatter 是召回的关键：

```markdown
---
name: playwright-skill
description: Complete browser automation with Playwright. Auto-detects dev servers,
  writes clean test scripts to /tmp. Test pages, fill forms, take screenshots,
  check responsive design, validate UX, test login flows, check links,
  automate any browser task. Use when user wants to test websites...
---
```

`description` 写得越具体，Agent 越能在正确的时机加载它。这里点名了能力（test pages / fill forms / screenshots / login flows）和触发条件（"Use when..."），等于给召回模型做了标注。

**渐进式披露（Progressive Disclosure）**是这个项目最值得抄的设计：SKILL.md 正文只有 453 行，只放"关键工作流 + 高频模式"，完整 Playwright API 参考（选择器、网络拦截、视觉回归、移动端模拟、性能测试）全部下沉到 `API_REFERENCE.md`，Agent 只有遇到对应任务才去读。对比把整本 Playwright 文档塞进 system prompt 的做法，上下文占用差了 10 倍不止。

SKILL.md 里强制的执行工作流：

1. **先检测 dev server**（localhost 场景）：`require('./lib/helpers').detectDevServers()`，命中 1 个直接用，多个让用户选，0 个就问 URL
2. **测试脚本一律写 /tmp**：`/tmp/playwright-test-*.js`，绝不污染项目目录
3. **默认可见浏览器**：`headless: false` + `slowMo: 100`，让执行过程可观察、可调试
4. **URL 参数化**：检测到的地址放进 `TARGET_URL` 常量，脚本可复用

## 三、run.js：通用执行器的三个设计点

`run.js` 是"零模块解析错误"的关键，源码 228 行，三个设计点逐个看。

**设计点 1：三种代码输入方式**

```javascript
function getCodeToExecute() {
  const args = process.argv.slice(2);

  // Case 1: 文件路径
  if (args.length > 0 && fs.existsSync(args[0])) {
    return fs.readFileSync(path.resolve(args[0]), 'utf8');
  }
  // Case 2: 内联代码
  if (args.length > 0) return args.join(' ');
  // Case 3: stdin
  if (!process.stdin.isTTY) return fs.readFileSync(0, 'utf8');
  process.exit(1);
}
```

Agent 生成的代码可能落在文件里、命令行参数里或 stdin 里，执行器统一收敛成字符串再执行——这是"通用"二字的来源。

**设计点 2：自动包装 + 错误兜底**

```javascript
function wrapCodeIfNeeded(code) {
  const hasRequire = code.includes('require(');
  const hasAsyncIIFE = code.includes('(async () => {');

  if (hasRequire && hasAsyncIIFE) return code;       // 完整脚本，原样执行

  if (!hasRequire) {                                  // 裸 Playwright 命令，补全模板
    return `
const { chromium, firefox, webkit, devices } = require('playwright');
const helpers = require('./lib/helpers');
(async () => {
  try {
    ${code}
  } catch (error) {
    console.error('❌ Automation error:', error.message);
    process.exit(1);
  }
})();`;
  }
  // 有 require 但缺 async 包装，只补 IIFE
  ...
}
```

LLM 生成的代码经常"缺头少尾"——忘了 require、忘了包 async 函数。执行器做**防御性包装**：检测到裸命令就自动补全 import 和 try-catch，未捕获异常转成 `process.exit(1)`，Agent 能根据退出码判断失败并自我修正。

**设计点 3：chdir + require 延迟清理**

```javascript
process.chdir(__dirname);   // 切到 skill 目录，保证 require('playwright') 能解析

// 执行前清理上次遗留的 temp 文件，避免竞态
function cleanupOldTempFiles() {
  const files = fs.readdirSync(__dirname);
  files.filter(f => f.startsWith('.temp-execution-') && f.endsWith('.js'))
       .forEach(f => fs.unlinkSync(path.join(__dirname, f)));
}

// 写临时文件后 require 执行
const tempFile = path.join(__dirname, `.temp-execution-${Date.now()}.js`);
fs.writeFileSync(tempFile, code, 'utf8');
require(tempFile);
// 注意：不立即删除，留给下一次运行清理
```

三个细节都很讲究：

- `process.chdir(__dirname)` 解决模块解析问题。Node 的 `require` 解析以**当前文件所在目录**为准，Agent 如果在任意 cwd 直接 `node /tmp/xxx.js`，`require('playwright')` 大概率报 `MODULE_NOT_FOUND`。chdir 到 skill 目录后，临时文件也写在 skill 目录里，解析链路就稳定了。
- 用 `require()` 而不是 `child_process.exec` 执行，省一次进程启动，错误栈也完整。
- 临时文件**不立即删除**——立即删会和长耗时异步操作（比如慢速页面加载）产生竞态；改成"下次运行前清理"，简单且安全。

## 四、一次完整的 Agent 测试会话

把整个流程串起来看架构：

```
用户: "测一下登录流程"
  │
  ▼
┌─────────────────────────────────────────────┐
│ Claude Code (Agent)                         │
│  1. 读取 SKILL.md (渐进式披露，按需加载)      │
│  2. detectDevServers() 检测本地服务           │
│  3. 写 /tmp/playwright-test-login.js         │
│  4. cd $SKILL_DIR && node run.js <脚本>      │
└─────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────┐
│ run.js (Universal Executor)                 │
│  chdir → 包装代码 → 写 temp → require 执行   │
│  输出 console + 截图到 /tmp                  │
└─────────────────────────────────────────────┘
  │
  ▼
Agent 读输出 → 判断成败 → 失败则改写脚本重试 → 返回结论
```

Agent 现场生成的登录测试脚本长这样：

```javascript
// /tmp/playwright-test-login.js
const { chromium } = require('playwright');

const TARGET_URL = 'http://localhost:3001'; // detectDevServers 检测到的

(async () => {
  const browser = await chromium.launch({ headless: false, slowMo: 100 });
  const page = await browser.newPage();

  await page.goto(`${TARGET_URL}/login`);
  await page.fill('input[name="email"]', 'test@example.com');
  await page.fill('input[name="password"]', 'password123');
  await page.click('button[type="submit"]');

  // 用 waitForURL 断言跳转，而不是固定 sleep
  await page.waitForURL('**/dashboard');
  console.log('✅ Login successful, redirected to dashboard');

  await page.screenshot({ path: '/tmp/login-result.png' });
  await browser.close();
})();
```

注意这里的**断言方式**：`waitForURL('**/dashboard')`、`waitForSelector('.success-message')` 这类条件等待，SKILL.md 里明确禁止固定 `sleep`。这保证了 Agent 生成的代码天然具备 Playwright 的自动等待语义，而不是靠猜时间。

## 五、与传统测试方式的对比

| 维度 | Playwright Test（手写） | Agent Skill（本方案） | MCP Browser 工具 |
|---|---|---|---|
| 用例编写 | 人写代码 | 自然语言描述，AI 生成 | 工具调用参数 |
| 断言 | 代码断言 | AI 生成断言 + 执行结果回读 | 工具返回 DOM/截图 |
| 覆盖场景 | 预置用例集 | 任意临时任务 | 工具暴露的能力 |
| 稳定性 | 高（确定性） | 中（LLM 生成有随机性） | 中 |
| 维护成本 | 高（页面变了改代码） | 低（重新描述即可） | 低 |
| 上下文开销 | 无 | 低（渐进式披露） | 工具定义常驻 |
| 适合场景 | 回归测试、CI 基线 | 探索性测试、临时验证、调试 | 固定原子操作 |

结论不是"谁取代谁"：**Agent Skill 解决的是探索性测试和临时验证**（"帮我看看这个表单能不能提交"），手写用例仍是 CI 回归的稳定基线。两者互补，不是替代。

## 六、踩坑记录与实践建议

把源码里的设计反推成踩过的坑，这些经验直接可复用：

1. **模块解析错误是最常见的失败模式**。Agent 在不同 cwd 下执行脚本，`require('playwright')` 时好时坏。解法就是 run.js 的 `process.chdir(__dirname)` + 统一入口，禁止 Agent 直接 `node /tmp/xxx.js`。
2. **固定 sleep 是 flaky 的根源**。SKILL.md 强制 `waitForURL` / `waitForSelector` / `waitForLoadState`，本质是把 Playwright 的 auto-wait 能力交给生成的代码。
3. **可见浏览器是调试利器**。默认 `headless: false` + `slowMo: 100`，执行过程肉眼可见，Agent 截图返回结果，人机都能确认"刚才到底发生了什么"。
4. **temp 文件要防竞态**。立即删除临时文件会打断长耗时操作，延迟到下次运行前清理，简单可靠。
5. **给自动化流量打标**。项目支持 `PW_HEADER_NAME` / `PW_HEADER_VALUE` 环境变量注入自定义 Header，后端可以识别"这是自动化测试流量"，还能要求 LLM 优化的纯文本响应（而不是渲染后的 HTML），降低 Agent 解析成本。

实践建议：本地探索用 `headless: false`，跑 CI 时切 `headless: true` 并让脚本以退出码表达结果；`TARGET_URL` 一律参数化，否则脚本无法复用。

## 七、进阶方向

- **接进 CI**：把 Agent 生成的脚本沉淀为固定用例，headless 模式跑进流水线，用退出码 + 截图归档做失败排查；
- **视觉回归**：API_REFERENCE 里已覆盖截图对比，配合像素级 diff 可以做无人值守的 UI 回归；
- **多 Agent 协作**：agentic-qe 这类开源 QE 平台已经在做"Agent 编排测试任务"，Skill 模式会是它们的标准化底座。

**总结**：playwright-skill 的架构价值不在于"用 AI 写测试"这个表象，而在于三个可复用的工程模式——**渐进式披露控制上下文成本、防御性代码包装兜底 LLM 输出、统一执行入口消除环境不确定性**。这套模式可以平移到你自己的任何 Agent 工具链里：给 Agent 装"技能"，比给它一堆工具参数，更接近它真正需要的自由度和可靠性。
